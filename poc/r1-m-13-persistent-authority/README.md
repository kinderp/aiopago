# R1-M-13 persistent authority / restart authenticity PoC

Status: **WINDOWS DISTINCT-IDENTITY RESTART/CRASH FOUNDATION POC PASS; PRODUCTION WRITERS UNCHANGED**.

This directory is non-production architecture/PoC material outside the npm `files` allowlist. It does not migrate any Aiopago writer and does not change package or production behavior.

## Threat boundary retained

P0 is arbitrary JavaScript running as the ordinary interactive Windows user. It may read package/project files, create attacker-owned copies, execute same-PID/Worker code, monkeypatch process/environment APIs, invoke user-accessible Windows APIs, and directly modify ordinary user-owned project state. The test does not expand the threat model to administrator/SYSTEM compromise, modification of genuinely protected service installation/state, or code deliberately injected into an already trusted P1S/P2 process.

Starting the genuine CLI is not itself treated as malware resistance. A public startup/control request may establish an interactive session, but it must never directly name the privileged mutation. Human/TUI authorization, repository/task/plan/session/lifecycle binding, and the private P1S→P2 session remain separate production obligations. This round tests durable authority authenticity, not whether endpoint malware can synthesize terminal input.

## Same-user experiment

Run on Windows x64:

```text
node poc/r1-m-13-persistent-authority/same-user-anchor.test.mjs
```

The harness creates only uniquely named temporary test data and cleans it. Each attack executes in a fresh PowerShell process under the same ordinary user as the P0 Node harness.

| Primitive | Raw secret readable by P0? | P0 can use protected operation? | P0 can delete/replace? | Restart-stable? | Authority distinct from P0? | Verdict |
|---|---:|---:|---:|---:|---:|---|
| NTFS file with current-user-only ACL | Yes | Yes | Yes; ACL change also proved | Yes | No | Reject |
| DPAPI `CurrentUser` | Yes, by calling `Unprotect` | Yes | Yes | Yes | No | Reject |
| Windows current-user PasswordVault/Credential Locker | Yes, by `RetrievePassword` | Yes | Yes | Yes | No | Reject |
| CNG software-KSP persisted non-exportable ECDSA key | No export | **Yes; separate P0 process signed 64 bytes** | Yes; delete/recreate changed fingerprint | Yes | No | Reject |
| TPM/platform-KSP persisted non-exportable ECDSA key | No export | **Yes; separate P0 process signed 64 bytes** | Yes; delete/recreate changed fingerprint | Yes | No | Reject |

The host exposed both Microsoft Software Key Storage Provider and Microsoft Platform Crypto Provider. The TPM-backed test is decisive: hardware non-exportability did not authenticate the caller. Same-user P0 opened the persisted key by name and used it as a signing oracle. CurrentUser certificate stores are not a stronger identity boundary: their private operations are backed by user-accessible CAPI/CNG key material and inherit the same caller identity problem. Machine-wide stores can be ACLed to a service identity, but that is the distinct-identity model below, not a same-user anchor.

Decision:

```text
PERSISTENT AUTHORITY REQUIRES A DISTINCT OS SECURITY IDENTITY
```

## Selected Windows identity model

Use a native P1S Windows service under **LocalService** plus the service-specific SID `NT SERVICE\AiopagoR1M13Poc`. LocalService alone is shared and is never granted on protected DACLs.

`RESTRICTED` SID type was physically attempted first. P1S entered, but dynamically linked Node and `whoami.exe` children both failed loader initialization with `0xc0000142`. The test did not weaken Windows system-path ACLs to force that token through. The passing oracle used SID type `UNRESTRICTED`, which still places the unique service SID in the token; protected ACLs grant only that SID, SYSTEM, and Administrators. Running as the invoking user, NetworkService, and LocalSystem remain rejected.

The administrator provisioned the service registration, protected directories, protected executable/runtime copies, and explicit Administrators ownership. P1S generated its key and canonical state itself after service entry.

## Executed restart oracle

```text
P0 ordinary user / public JS
       |
       | startup/control only; no mutation method
       v
P1S native Windows service
  LocalService + service-specific SID (UNRESTRICTED SID type)
  owns canonical state and Ed25519 private key file
       |
       | broker-created anonymous inherited pipes
       | per-session CAP_priv, fixed semantic request only
       v
P2 privileged Node/Pi runtime
```

P1S canonical state under `%ProgramData%\Aiopago\R1M13Poc\canonical` contains:

- `identity.ed25519`: generated by P1S; never projected;
- `state.json`: schema, stable public key, monotonic sequence, request ID, payload digest, previous-record digest, record digest and Ed25519 signature;
- `requests.json` or equivalent protected request-ID result map for duplicate/conflict handling.

The public project projection contains only the public key/fingerprint, signed records and status. It is disposable and never loaded as canonical input.

The representative private operation is fixed to `POC_OPERATION_TERMINAL`; there is no eval, module loading, arbitrary Runner method, arbitrary filesystem writer, or general RPC. An exact duplicate returns the protected recorded result, while reuse of a request ID with changed payload is rejected. The service control manager surface can start/stop/query the test service but cannot request the sentinel. The service itself creates P2's anonymous handles and session capability; P0 receives neither.

### Atomic/crash rule

For the bounded PoC, P1S writes a complete next-state temporary file, flushes it, atomically replaces canonical state, then emits the projection. A crash before replacement leaves the previous sequence canonical; a crash after replacement leaves the complete signed next sequence canonical. Projection may be missing or stale and is regenerated. Production still requires a reviewed database transaction/WAL, directory durability, corruption recovery, backup/anti-rollback and multi-record commit protocol.

Runtime attacks must be attempted, not inferred: read/copy/delete/replace key; write/delete/rollback canonical state; take ownership/change DACL; run an attacker-owned executable copy; open a CNG/key API signing oracle; forge/delete/replay projection. Expected P0 result for every canonical/key mutation is Windows `ACCESS_DENIED`; projection attacks succeed but are ignored/regenerated by P1S.


This session proved high integrity, enabled Administrators membership, `net session` exit 0, and SCM create/query/delete authority. The exact source procedures are `provision-service.ps1`, `service-broker.go`, `medium-launcher/main.go`, `p0-medium-attack.mjs`, `p2-service-runtime.mjs`, and `cleanup-service.ps1`. Machine-specific, non-secret evidence is in `windows-elevated-oracle-evidence.json`; private key bytes are absent.

The real medium P0 token was duplicated from Explorer and reported `S-1-16-8192` with Administrators deny-only. P1S reported LocalService `S-1-5-19`, the service SID, and service integrity `S-1-16-16384`. Clean restart retained fingerprint `d33e4cb16aa25db116145190b004a981ba34cbc47875fe4560c53c080901bcf1`; sequence advanced from 1 to 2 only through intended P2. P0 key/canonical/binary/service-config attacks were denied, while projection forgery succeeded but was ignored.

The deterministic crash point was after a complete flushed temporary state and before atomic replace. Canonical SHA remained unchanged at sequence 2; restart detected and discarded the uncommitted temporary state. Exact duplicate was idempotent, changed-payload reuse conflicted, and an exact older signed projection replay never became canonical.

## Cross-platform mapping

- **Windows (foundation physically passed):** LocalService plus unique service SID (UNRESTRICTED SID type after the documented RESTRICTED child-loader blocker); protected `%ProgramData%\Aiopago\R1M13Poc`; SCM lifecycle control; P1S-created anonymous inherited pipes to P2.
- **Linux (design only):** dedicated locked `aiopago` system user via systemd; `/var/lib/aiopago` mode `0700` owned by that user; root-owned unit; P1S-created `socketpair`/pipes to P2; optional Unix socket with peer credentials for startup control, not privileged semantic authority.
- **macOS (design only):** launchd system daemon under dedicated `_aiopago` user; `/Library/Application Support/Aiopago` service-owned protected state; inherited pipes/socketpair or narrowly designed XPC control plus private P2 channel.

No Linux or macOS runtime PASS is claimed.

## Packaging and modes

Retain the preferred meta npm package plus exact platform packages. Add an explicit signed secure-broker installer or `aio secure-broker install` provisioning command. It may request elevation interactively but must not run silently in npm `postinstall`, and packages must not download executables over the network at install time. Upgrade must stop the service, verify signed/version-coupled binaries and preserve protected canonical state/key with rollback-safe migration. Uninstall must explicitly choose retain/export vs administrator deletion of canonical state.

Aiopago should expose honest modes later:

1. **SECURE AUTHORITY MODE:** protected broker installed and healthy; R1-M-13 authority contract may apply after writer migration and security gates.
2. **PORTABLE/DEV MODE:** npm-only current-user execution; useful for development/portable workflows, but no R1-M-13 privileged-authority isolation claim.

The modes must have distinct status/diagnostics/security labels. This split is analyzed only, not implemented.
