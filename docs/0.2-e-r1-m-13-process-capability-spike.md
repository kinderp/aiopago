# 0.2-E R1-M-13 process-capability feasibility spike

Status: **NATIVE PROCESS/CAPABILITY SUB-PROOF PASS; PRODUCTION ARCHITECTURE BLOCKED**

Candidate examined: `7ef2d831caaa16c5cf6ce44edae0c671a7e20e6f`

Threat-model decision: activated-source reconstruction is in scope. The exclusion first added for that reconstruction at this candidate is invalid and is not used here.

## Constraint and current result

The in-scope attacker can execute arbitrary JavaScript in an existing consumer PID, read every installed Aiopago artifact, copy and transform those bytes, evaluate data URLs/temporary modules/vm/Workers, and patch genuine Pi in that PID. Aiopago may still treat physical modification of the trusted installed tree and a deliberately attacker-preloaded new process as the historically excluded installation/process compromise cases.

The legitimate operational child currently possesses no non-reconstructible capability. Its distinguishing inputs are the public bundle bytes, the public physical-location marker replacement, a public appended function call, sanitized environment values, argv, and a fresh PID. Only the fresh PID is not literally copied, but no OS-backed authority is bound to that PID. The privileged implementation and its ordinary filesystem/SQLite mutation primitives are self-contained in the reconstructed JavaScript.

The standalone reproducer `test/reproducers/r1-m-13-activated-source.mjs` packed and installed the untouched candidate, imported genuine Pi 0.83.0, reconstructed the public bin transformation in an attacker-owned base64 data URL, and observed in one consumer PID:

- installed `dist/cli-entry.mjs` modified: no;
- extension factories: 1;
- commands: 4;
- handlers: 10;
- Runner authority: 1;
- `OP-FORGED`: `TERMINAL / KNOWN_SUCCESS / READ_ONLY`;
- durable `HUMAN_TAKEOVER`: present.

## Ratification decision and bounded experiment

The preferred deployment direction remains **native capability launcher plus mutation broker**, not an administrator-installed permanent service, because it is the only candidate that could retain user-scoped, on-demand, portable operation. The direction is ratified only as the process boundary to investigate; it is **not ratified as a complete durable-authority architecture**.

`poc/r1-m-13-native-capability/` implements a bounded P0→P1→P2 flow without changing production code:

- P1 is a CGO-free Go executable and is the only component that creates a 256-bit `crypto/rand` capability;
- P1 verifies a build-bound P2 source digest, uses a build-bound absolute Node executable rather than P0's mutable `process.execPath`, sanitizes the P2 environment, and creates dedicated anonymous stdin/stdout protocol pipes;
- P2 is deliberately readable JavaScript and receives the capability only over those inherited pipes;
- P1 accepts only one fixed `POC_OPERATION_TERMINAL` request bound to exact repository, task, plan, session, lifecycle and takeover-generation values;
- the protocol has only `HELLO`, `SESSION_BIND`, `AUTHORIZE_MUTATION`, `MUTATION_RESULT`, and `SHUTDOWN`; every frame has version, request ID, operation type, bounded payload and explicit result; malformed/unknown/oversized input fails closed;
- no eval, source transport, module loading, arbitrary method/function name, generic journal call, or generic writer exists.

One Windows x64 run observed `P0=8604`, `P1=16340`, and `P2=23212`, with P1 parented by P0 and P2 parented by P1. P0, P1 and P2 were distinct. CAP_priv was absent from package files, P0 memory, argv and environment; it existed only in P1 and intended P2 for that process lifetime. The positive sentinel count was 1. Absolute import, Worker, copied source, data URL, temporary source, genuine-Pi patch, mutable `process.execPath`, spawn/spawnSync and CJS/ESM synchronization patches, env/argv changes, a fake capability, old-message/digest replay, duplicate request and changed-payload request-ID replay produced zero unauthorized broker mutations. Duplicate creation count was zero and P2/pipe cleanup passed. Generated binaries and records stayed under the OS temporary directory.

The exact activated-source reproducer was rerun separately and still captured genuine Pi 0.83.0, one factory, four commands, ten handlers, Runner authority, forged `OP-FORGED`, and one `HUMAN_TAKEOVER`, while installed bytes remained unchanged. This proves the PoC did not cosmetically alter or suppress the original exploit.

### Critical durable-authenticity result

The process sub-proof does **not** answer the full security question. P0 has the same user filesystem rights as P1 and can write `.guardian/runtime/guardian.sqlite`, `TASK_PLAN.md`, plan history/lock files, checkpoint/manifest files, and any portable sidecar. In the experiment P0 rewrote the sentinel with an attacker operation while retaining the genuine record MAC. The live native P1 rejected that state and restored the authentic record because P1 still held its ephemeral key. Attacker-accepted mutation count remained zero.

After P1 exits, however, a later portable P1 does not possess the old random capability. A public verification key stored beside the record can be replaced with the record; a package/static private secret is forbidden and extractable; ordinary same-user permissions and same-user credential stores do not distinguish P0. The restart experiment therefore reports `UNVERIFIABLE_WITHOUT_PERSISTENT_TRUST_ANCHOR`. Aiopago's existing resume/recovery semantics require old durable state to remain authoritative across process lifetimes. Consequently an ephemeral launcher/broker alone cannot prove whether later SQLite/journal/file state is authentic.

This is a blocking result, not a request for another JS gate. The minimum next architecture decision must choose and experimentally prove either (a) an OS-protected persistent signing identity/trust anchor with credible Windows/Linux/macOS semantics and no P0 signing oracle, or (b) a protected long-lived broker/service that remains the sole acceptance authority. Reducing cross-process durable semantics would conflict with the existing product and is not authorized.

`process.execPath` is also directly observed as writable and configurable in Node 22.19.0. It cannot be the trust root of a bootstrap running in hostile parent JavaScript.

## Alternative A — pure JavaScript

No pure-JS construction can create the required distinction. A function name, closure, WeakMap, Symbol, private field, package export, source marker, source transform, environment/argv value, worker state, process property, `import.meta.main`, filename, or static token is interpreted by the same attacker-controlled JavaScript engine. If a JS check guards construction, the attacker can remove it from the attacker-owned copy. If JS retains the filesystem/SQLite writer behind that check, the attacker can invoke that writer after removing the check.

Therefore another predicate would be a fourth cosmetic remediation. Pure JS is not recommended for a proof of concept.

## Alternative B — privileged out-of-process service

A service can provide a real boundary only if it is trusted from process start and exclusively owns mutation authority. Merely moving the existing bundle into another ordinary Node process is insufficient: public parent JavaScript controls `spawn`, mutable `process.execPath`, environment, argv, and which program is launched; an attacker can also connect to an unrestricted local service.

A capable service design would have these properties:

- public code receives only frozen serialized projections and error records;
- privileged Runner, Pi factory, handlers, storage, tracker, handoff, takeover, resume, recovery, authorization, admission, dispatch, and lifecycle closures never enter P0;
- the service or broker, not transformable client JS, enforces every privileged mutation;
- authentication uses an inherited anonymous OS channel or an OS-service identity, never a static package secret, argv, environment, global, or named endpoint alone;
- a long-lived endpoint uses OS ACL/peer identity plus a launcher-created per-instance channel; same-user reachability alone is not authorization.

A minimum framed protocol would use canonical length-bounded messages with exact versioned fields. Public intent names should be no broader than existing product behavior: `status`, `why`, `next`, `plan`, `init`, `start`, and an interactive attachment. Existing `/aio handoff`, `takeover`, `resume`, and recovery commands should remain inside the privileged Pi/TUI session rather than becoming generic public RPC methods. There must be no `eval`, arbitrary module load, callback registration, arbitrary Runner method call, generic journal write, generic operation completion, or raw storage transaction.

Each mutating request would bind a request ID, launcher/runtime instance, canonical repository/task identity, session/Runner identity where applicable, expected plan revision and digest, expected latch/handoff identity, and deadline. The broker must re-observe these values rather than trust client claims. Existing durable authorization/admission/idempotency records can support exactly-once behavior. Duplicate request IDs return the recorded result; stale revisions, sessions, handoffs, or latches fail closed. Client death cancels only unadmitted work; after admission the existing durable outcome/reconciliation semantics apply. This must not introduce 0.2-F durable stop/resume.

Errors must be closed serialized code/message/details records, never Error objects or closures. Human takeover and handoff confirmation remain service-side TUI actions bound to the current trusted session. For interactive Pi, the practical design is to run the entire Pi/TUI in the trusted runtime and attach its standard input/output terminal handles through the launcher. Serializing Pi extension factories or handlers to a public renderer would recreate the defect. EOF, child failure, and process death should terminate the current interactive process and use existing failure/reconciliation semantics, without automatic resume.

Windows can implement private channels with anonymous pipes or restricted named pipes, explicit handle lists, non-inheritable P0 handles, and a Job Object for lifetime supervision. POSIX needs `socketpair`/inherited file descriptors and equivalent lifetime handling. These are new native/platform concerns absent from this repository.

## Alternative C — native/private launcher

A valid native launcher must start outside attacker-controlled JS state, derive the actual runtime executable from an OS/bundled trust root rather than mutable `process.execPath`, clear resolver/preload environment before Node initialization, create `CAP_priv` after entry into P1, and pass only a private inherited OS endpoint to the privileged runtime. P0 must receive neither endpoint nor nonce.

A native launcher that merely appends the same public invocation or supplies a token to a self-contained JS bundle is not sufficient. The attacker can remove the token check and use the copied JS writer. The channel must terminate at a broker/external authority that is required for mutation, and public/reconstructed code must contain no direct privileged fallback.

The repository now contains only the non-production Go PoC source under `poc/`; it still has no production native build, prebuilt artifact matrix, signing flow, Node SEA flow, or native release mechanism. Implementing and validating Windows, Linux, and macOS launcher/broker artifacts remains outside a bounded 0.2-E patch.

## Alternative D — separate executable/artifact

An actual process-only executable could be useful as the launcher, broker, or complete privileged runtime. It must reject preload/injection, expose only serialized intent/results, and keep its dynamic capability internal. “Compiled” or “bundled” does not itself establish authority: an embedded JS blob with a shipped key or removable JS check is still reconstructible.

Node SEA is not currently supported by this repository. It would require a new per-platform artifact/build/injection/signing pipeline and proof that the exact Node/Pi combination cannot accept attacker preload or expose an importable embedded privileged program. It would also materially increase package size and complicate Pi 0.83.0's external package layout. SEA might package P2, but does not replace the launcher/broker capability or permission boundary and is not selected here.

## Alternative E — OS/file permissions

A service account or administrator-installed protected directory can make privileged implementation/key/state unavailable to the ordinary package consumer. This provides the clearest external authority: public algorithms do not grant the service identity, protected key, or service-owned handles.

It changes the deployment contract from a portable npm package operating as the current user to an installed service/application, potentially requiring elevation, service lifecycle management, upgrades, ACL repair, and per-platform installation. That requirement cannot be introduced silently in 0.2-E.

## Minimum secure process graph requiring a product decision

```text
attacker/public JS PID P0
        |
        | may request a supported command or exec launcher;
        | transfers argv/target and terminal bytes only; no CAP_priv
        v
native launcher + mutation broker/service PID P1
        |
        | creates anonymous OS channel and CAP_priv after entering P1;
        | chooses/sanitizes trusted runtime without process.execPath from JS;
        | retains mutation endpoint and authoritative storage operations
        v
privileged Node runtime PID P2
        |
        +-- GuardianRunner
        +-- genuine Pi 0.83.0 and TUI
        +-- extension factory/handlers
        +-- narrow broker client over inherited endpoint
```

- **P0 → P1:** caller is public/attacker JS or the user's shell; callee is the native launcher; distinct PID; target/command/terminal handles are visible to P0; no capability or privileged object is returned. P1 treats all request fields as untrusted intent.
- **P1 → P2:** caller is trusted native P1; callee is sanitized trusted Node P2; distinct PID; exact runtime data and one private inherited channel endpoint are transferred. P0 owns no duplicate endpoint. `CAP_priv` is generated and owned after the P1 boundary and is usable only through the endpoint.
- **P2 → P1:** caller is trusted Runner code; callee is the mutation broker; strict semantic operations with task/session/plan/latch/handoff identities are transferred. P1 owns durable mutation authority and exactly-once admission. No generic function, module, method, or writer is accepted.
- **P2 ↔ terminal:** only input/output bytes and process exit status cross. Pi objects, closures, handlers, storage, and capability material do not.

The exact protocol and broker split require architecture work. In particular, P1 cannot merely bless publicly reconstructible storage JS with a token; it must enforce the mutation itself or use an equivalent protected external authority.

## Channel and process design

| Platform | Primitive | Created by | Inherited by | Visible to P0? | Forgeable by P0? | Lifetime |
|---|---|---|---|---:|---:|---|
| Windows x64 PoC | `os/exec` anonymous stdin/stdout pipe handles with intended child inheritance | P1 | P2 only | No handle ownership | No; P0 can create lookalike pipes but cannot connect them to P1 | P1/P2 session; closed on exit |
| Windows production candidate | explicit anonymous handles with `AdditionalInheritedHandles`/handle-list control, or a restricted first-instance named pipe only if Node handle integration requires it | P1 | exact P2 | Must be no | Must be no; named endpoint would additionally need ACL, first-instance and capability/session binding | Runner lifetime |
| Linux x64 | inherited anonymous pipes or `socketpair`, close-on-exec everywhere else | P1 | exact P2 fd(s) | No fd ownership | No | Runner lifetime |
| macOS arm64 | inherited pipes or `socketpair`, close-on-exec everywhere else | P1 | exact P2 fd(s) | No fd ownership | No | Runner lifetime |

The PoC uses P2 stdin/stdout for the private protocol, so it does not prove interactive Pi compatibility. Production must either reserve independent handles for broker IPC while directly attaching terminal handles to P2, or implement a native terminal/ConPTY proxy with bounded terminal messages. A discoverable same-user socket or named pipe alone is not authority.

Future production requests must be re-observed and bound by P1 to canonical repository identity/path, task ID, plan revision and digest, broker session, Runner instance and lifecycle epoch, takeover generation, handoff/resume/recovery identity, operation ID and request idempotency key. P0 claims are intent only. P2's human prompt does not authorize a generic method; P1 accepts a fixed semantic transition only after checking its own protected state. Duplicates return recorded results and changed payload under an existing request ID fails closed.

P1 must be the actual user-facing native entrypoint. A hostile JavaScript P0 calling `spawn` correctly cannot be the trust root: mutable `process.execPath`, spawn monkeypatching and environment selection can deny or redirect its own request. The normal shell/npm command must ultimately exec the platform binary itself; P1 then chooses and verifies P2 independently. The PoC build-bound an absolute Node path and P2 digest. A production release needs either a bundled/pinned runtime or a native, installation-relative, signed/digested runtime identity; a P0-supplied Node path is forbidden.

## Packaging decision

- **Model 1 — all platform binaries in `aiopago`:** deterministic and offline, but ships irrelevant binaries to every user and still needs a package-manager-safe native selection/materialization mechanism. Current three stripped helpers total about 7.2 MB before compression, excluding any runtime.
- **Model 2 — meta-package plus platform packages:** **recommended**, using exact optional dependencies such as `aiopago-win32-x64`, `aiopago-linux-x64`, and `aiopago-darwin-arm64`. Installation may select/copy/link only the locally installed signed binary; invocation must not pass through a Node security predicate. The npm bin-link behavior for native executables and global/local installs needs its own packaging prototype. No generated binary belongs in this PoC commit.
- **Model 3 — postinstall network download:** rejected because network availability, redirect/checksum/signature hosting, cache, rollback and compromise response add unnecessary supply-chain complexity.

Model 2 adds per-platform publish ordering, exact version coupling, checksums/signatures, provenance, optional-dependency diagnostics and unsupported-platform errors. It avoids download-at-install and irrelevant binaries. Current metadata declares only Node `>=22.19.0` and no `os`/`cpu`; repository-required initial targets are Windows x64, Linux x64 and macOS arm64. No claim is made for other architectures.

## Interactive feasibility and unresolved proof

P2 must retain genuine Pi 0.83.0, `GuardianRunner`, InteractiveMode/TUI, extension factory/handlers and all session objects. P0 may receive only bytes and exit status. Preferred production behavior is direct P2 ownership of stdin/stdout/stderr and terminal size, with a distinct private broker channel. P1 must forward/coordinate Ctrl-C and termination, propagate child exit, close channels on crash/EOF and avoid automatic resume. Windows likely needs explicit handle lists plus Job Object/ConPTY analysis; POSIX needs process-group signal forwarding and terminal foreground ownership. Takeover remains a P2 human action whose durable latch mutation is authorized by P1. No 0.2-F stop/resume state is introduced.

The current PoC proves protocol cleanup but not terminal size, signals, Ctrl-C, InteractiveMode rendering, replacement-session takeover, Linux execution or macOS execution. Existing semantic portability is therefore not yet demonstrated.

This should be represented under existing roadmap conventions as an explicit **0.2-E security/foundation work unit: R1-M-13 Capability Boundary**, with its own plan/checkpoints and architecture acceptance gates. It is not 0.2-F and does not invent a new public version.

## Decision

The experiment validates that a small native P1 can create and transport a real ephemeral process capability and can prevent reconstructed/copied JavaScript from invoking one live broker mutation. It also demonstrates that this is insufficient for Aiopago's durable authority: restart-time authenticity and interactive Pi/TUI portability remain unproved. Therefore the complete architecture PoC is blocked even though the bounded process sub-proof passed.

**R1-M-13 ARCHITECTURAL BLOCKER**

Production code is intentionally unchanged. The minimum next decision is protected persistent authority: choose an OS-protected cross-platform trust anchor or a protected long-lived broker/service, then prove restart authenticity and dedicated interactive IPC before production migration. PR #31 remains draft, independent gate remains 0/2, and 0.2-F must not start.
