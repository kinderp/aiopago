# Aiopago 0.2-C — Minimal Intent Adapter

## Status and scope

0.2-C is **READY FOR INDEPENDENT REVIEW**. It adds a provider-neutral programmatic adapter with five semantic operations:

- `plan.observe`
- `plan.propose`
- `plan.validate`
- `plan.diff`
- `plan.apply`

The adapter accepts structured JSON data only. It does not parse objectives, invoke an LLM/provider, choose work, approve a proposal, or decide whether a valid proposal should be applied.

## Architecture and authority

```text
caller / future structured producer
        |
        v
0.2-C Intent Adapter (public package-root surface)
        |
        v
0.2-B PlanPort / PlanProposal (internal)
        |
        v
PlanRevisionWriter (internal controlled writer)
        |
        v
TASK_PLAN.md (sole current plan authority)
```

`TASK_PLAN.md` remains authoritative. An observation, intent, proposal object, diff, validation result, proposal registration, history snapshot, or `.guardian` record is not another authority. The adapter creates no Intent database, current-plan mirror, synchronization mechanism, Git commit, or HUMAN authorization.

The package root exports:

```js
import { plan, createPlanAdapter } from "aiopago";

// plan is bound to TASK_PLAN.md resolved from the importing process cwd.
const repositoryPlan = createPlanAdapter("/absolute/repository/TASK_PLAN.md");
```

The package root intentionally does not export `PlanPort`, `PlanProposal`, `PlanRevisionWriter`, raw replacement helpers, receipt state, owner-gate transition internals, or filesystem mutation primitives. `createPlanAdapter(path)` changes only which `TASK_PLAN.md` the adapter observes; it does not grant a raw writer surface.

## Strict JSON boundary

Every intent and serialized proposal entering 0.2-C is cloned into the existing strict JSON domain before it is trusted. Inputs reject custom prototypes, class instances, accessors, hidden or symbol keys, sparse/extended arrays, functions, `undefined`, non-finite numbers, `BigInt`, host objects, cycles, and excessive depth/node count. The clone prevents post-call caller mutation from changing a proposal.

A serialized proposal is reconstructed through the 0.2-B `PlanProposal` constructor. The adapter recomputes and verifies `proposal_digest`; caller object identity, prototype, class branding, and supplied digest are not authorization.

All successful adapter responses are detached plain JSON graphs and recursively frozen. They contain no mutable authority bytes or raw writer handle.

## `plan.observe()`

**Mutation:** none.

Returns an `aiopago.plan-observation/0.1.0` object:

```json
{
  "schema": "aiopago.plan-observation/0.1.0",
  "task_id": "TASK-...",
  "plan_revision_id": "PLAN-...",
  "content_digest": "sha256:...",
  "plan": { "schema_version": "0.1.0", "task_items": [] }
}
```

The digest is over the exact authoritative Markdown bytes, while `plan` is the strictly validated Ledger JSON block. Repeated reads of unchanged authority are semantically identical. Observation takes no plan-write lock and does not create `.guardian`. Missing, redirected, oversized, malformed UTF-8, ambiguous Markdown, invalid JSON, or semantically invalid Ledger authority fails closed.

## `plan.propose(intent)`

**Mutation:** none.

The request is exactly:

```json
{
  "schema": "aiopago.plan-intent/0.1.0",
  "proposal_id": "PPR-opaque-id",
  "producer": "my-structured-planner/1",
  "change_reason": "Revise the reviewed structured work sequence.",
  "candidate_plan": { "schema_version": "0.1.0", "task_items": [] }
}
```

`candidate_plan` is the complete desired Ledger, not a patch and not natural language. It must include a new `plan_revision_id`; its canonical `updated_at` becomes proposal `created_at`. The candidate's `requirements_version` becomes proposal requirements identity. The caller supplies the opaque proposal ID, producer, and bounded reason needed by the existing evidence model.

The adapter derives these fields exclusively from a fresh exact observation, never from the caller:

- `task_id`
- `base_plan_revision_id`
- `base_content_digest`

Unknown intent fields—including caller attempts to supply base identity—are rejected with `PLAN_INTENT_FIELDS_INVALID`. The candidate is reconstructed as `PlanProposal`, semantically validated, checked for owner-gate restrictions, materialized against the exact observation, and checked against the 32 MiB authority limit. Proposing does not change authority or create `.guardian` evidence.

The response is a frozen, serializable `aiopago.plan-proposal/0.1.0` payload plus its recomputed `proposal_digest`. It can be JSON serialized and later passed to `validate`, `diff`, or `apply`.

## `plan.validate(proposal)`

**Mutation:** none.

Validation reconstructs the proposal and verifies its digest, strict JSON shape, Ledger semantics, exact current task identity, exact base revision/digest, requirements consistency, Markdown materializability, owner-gate constraints, canonical schema mutation boundary, and size limits.

A current-base match returns an immutable `aiopago.plan-validation/0.1.0` result with `valid: true`, `stale: false`, proposal/base identity, and deterministic candidate authority digest. Invalid structure or semantics retains the specific validation error. A proposal that is internally valid but no longer matches current authority fails separately with `PLAN_PROPOSAL_STALE` and revision/digest match details.

Validation does not register a proposal, write history, acquire the mutation lock, or modify `TASK_PLAN.md`.

## `plan.diff(proposal)`

**Mutation:** none.

Diff reconstructs the proposal, requires its exact bound base to remain current, materializes the canonical candidate, and returns the existing `aiopago.plan-diff/0.1.0` result from `diffTaskPlans`. It reports deterministic Task fields and sorted added/removed/changed TaskItems. There is no second diff algorithm, hidden apply, proposal registration, or history write.

## `plan.apply(proposal)`

**Mutation:** controlled authority replacement and derived evidence.

This is the only `plan.*` operation that may replace `TASK_PLAN.md`. After strict adapter reconstruction and digest verification, it delegates directly to the same 0.2-B `PlanPort.apply` path. The adapter does not retry, rebase, replay, merge, repair, or relabel errors from that path.

Delegated invariants remain unchanged:

- exact-byte and revision CAS;
- owned plan-write lock and final pathname continuity attestation;
- 32 MiB authority limit and strict UTF-8/JSON/Ledger validation;
- exact immutable base history;
- immutable proposal registration and bounded commit intents;
- commit intent, filesystem witness, post-rename applied evidence, and durability behavior;
- maximum 128 durable attempts;
- same-runtime volatile receipt for idempotent success;
- restart/cross-process ambiguity remains fail-closed;
- no automatic Git commit;
- canonical schema required for generic mutation;
- generic owner-gate preservation and HUMAN latch.

## Concurrency, staleness, and recovery

A proposal is bound to one exact observation. If authority changes from A to C after proposal B was created:

- `plan.validate(B)` reports `PLAN_PROPOSAL_STALE`;
- `plan.diff(B)` reports the same stale relationship;
- `plan.apply(B)` delegates to 0.2-B and returns `PLAN_CAS_CONFLICT` (or the more specific existing recovery conflict where durable evidence makes that applicable);
- C is never overwritten and no silent rebase occurs.

A successful `apply` may be called again on the same adapter instance and receive the exact idempotent result when the private volatile receipt and filesystem fingerprint match. A new adapter/process cannot authenticate that receipt from disk; it returns `PLAN_RECOVERY_AMBIGUOUS`. Human reconciliation or a newly authorized proposal is required.

## Owner gate and legacy policy

Generic intent operations cannot introduce, remove, release, change, or restructure a `HANDOFF_CONFIRM/BLOCKED` owner gate. They cannot advance protected lifecycle status, change current/next items or next step, alter item status/topology, change the fixed command, or forge audit data. `satisfyOwnerGate` is deliberately absent from the adapter. The existing specialized HUMAN path remains the only release operation.

Supported historical Ledger remains readable through `observe`. Generic `propose`/`validate`/`diff`/`apply` mutation mechanics require canonical `aiopago.task-ledger/0.1.0`; legacy authority fails with `PLAN_LEGACY_MIGRATION_REQUIRED`. The adapter never silently migrates it.

## Error semantics

Errors retain `GuardianError`-compatible `code`, `message`, and optional `details`. Important categories include:

| Category | Representative code |
|---|---|
| Invalid intent JSON/shape | `PLAN_INTENT_JSON_DOMAIN_INVALID`, `PLAN_INTENT_FIELDS_INVALID` |
| Invalid/reconstructed proposal | `PLAN_ADAPTER_PROPOSAL_FIELDS_INVALID`, `PLAN_PROPOSAL_DIGEST_INVALID`, existing `PLAN_PROPOSAL_*` |
| Invalid Ledger/materialization | existing `LEDGER_*`, `PLAN_MATERIALIZATION_INVALID`, `PLAN_AUTHORITY_TOO_LARGE` |
| Valid but stale during preview | `PLAN_PROPOSAL_STALE` |
| Apply CAS/recovery conflict | `PLAN_CAS_CONFLICT`, `PLAN_PROPOSAL_RECOVERY_CONFLICT` |
| Owner latch/gate | `PLAN_OWNER_LATCH_BYPASS_FORBIDDEN`, `PLAN_OWNER_GATE_MUTATION_FORBIDDEN`, `OWNER_GATE_*` |
| Lock/recovery/provenance | `PLAN_WRITE_LOCKED`, `PLAN_RECOVERY_AMBIGUOUS`, `PLAN_PROVENANCE_INVALID` |
| Legacy mutation | `PLAN_LEGACY_MIGRATION_REQUIRED` |
| Attempt cap | `PLAN_ATTEMPT_LIMIT_REACHED` |

Security-critical 0.2-B errors are not swallowed or converted into generic adapter failures.

## Structured example

```js
import { createPlanAdapter } from "aiopago";

const plan = createPlanAdapter("./TASK_PLAN.md");
const observation = plan.observe();

// This object is produced externally using structured data only.
const candidate = structuredClone(observation.plan);
candidate.plan_revision_id = "PLAN-reviewed-2";
candidate.updated_at = "2026-08-21T12:00:00.000Z";
candidate.next_step = "Implement the next reviewed item.";

const proposal = plan.propose({
  schema: "aiopago.plan-intent/0.1.0",
  proposal_id: "PPR-reviewed-2",
  producer: "example-structured-producer/1",
  change_reason: "Use the reviewed structured candidate.",
  candidate_plan: candidate,
});

const validation = plan.validate(proposal);
const diff = plan.diff(proposal);
// A human or upper layer decides whether the diff should be applied.
const result = plan.apply(proposal);
```

## 0.2-D boundary

0.2-C includes no `aio start <objective>`, natural-language parsing, prompt-to-plan generation, provider SDK, model routing, planning loop, automatic next-work selection, automatic approval, autonomous apply policy, or interactive planning wizard. Those remain 0.2-D or later work.

## Test and acceptance matrix

| Area | Focused evidence |
|---|---|
| Observe | exact identity, deterministic/frozen response, malformed authority, no state |
| Propose | current base binding, spoof rejection, strict JSON attacks, mutation isolation, Ledger/owner gate/size, no state |
| Validate | valid result, forged digest/object, stale base, owner latch, legacy boundary, size, no state |
| Diff | deterministic canonical Task/TaskItem diff, no state |
| Apply | end-to-end bytes, CAS, lock, same-runtime retry, restart ambiguity, ID conflict, provenance, owner gate, legacy boundary, unchanged error codes |
| Full flow | observe → propose → validate → diff → inspect → apply |
| 0.2-B regressions | CAS/path continuity, lock, history, receipts, recovery, provenance, attempt cap, UTF-8, Markdown layouts, owner gate, strict JSON, durability |
| Package | root import, intended exports, internal writer non-export, packed runtime files |

Independent acceptance remains a separate two-round review gate. Developer self-review does not count toward it.
