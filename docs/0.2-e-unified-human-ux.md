# Aiopago 0.2-E — Unified Interactive Human UX

## Status and purpose

0.2-E unifies the deterministic human workflow shown by the external CLI and the Pi interactive extension. It does not add authority. One immutable, recomputed `aiopago.human-workflow-projection/0.2-e` view now supplies state, severity, headline, objective, current activity, progress, reason, one bounded next action, plan summary, runtime summary, human-control state, handoff guidance and optional technical diagnostics.

```text
authoritative/read-only observations
              |
              v
     projectHumanWorkflow()
          /          \
         v            v
 CLI presenters    Pi presenters
 status/why/next   /aio status/why/next
 plan              /aio plan
```

`formatGuardianStatus()` remains only as a compatibility technical presenter over that projection. It no longer independently decides state, reason or next action.

## Observation adapters

Two read environments feed the same projector:

- `observeHumanWorkflow()` discovers repository configuration, reads `TASK_PLAN.md`, and uses the conservative external runtime reader. It does not instantiate a Runner. External runtime absence, presence without a canonical verifier, concurrent SQLite sidecars, change during read and read failure remain explicitly unavailable or unverified; none becomes a healthy runtime claim.
- `observeRunnerHumanWorkflow()` reads the same plan authority and selected live Runner facts: session identity/model, latch, latest handoff, Git and context use. It exposes no storage, session manager, writer, service or callback. It compares plan, session, latch and handoff identity across the read and reports `RUNTIME_CHANGED_DURING_READ` rather than combining incompatible facts.

The live adapter is additive. It does not replace `TASK_PLAN.md`, GuardianStorage or Runner state with a view model. Both adapters preserve precise diagnostics where available. A verified live claim also carries an explicit task/revision/digest binding and must pass `validateRuntimeObservation()` before any positive projection: coherent live workflow/condition, session and Runner identities, latch state/generation/reason, optional handoff identity/state/failure, and bounded context/Git evidence. Missing, malformed, unknown, contradictory or task-mismatched verified evidence becomes `NEEDS_ATTENTION` with `RUNTIME_OBSERVATION_INVALID`. Explicitly unavailable/unverified external observations retain their conservative supported shape and do not require a live session identity.

## Projection and presentation

The projection is a detached, recursively frozen plain data graph. Selected nested diagnostics—including handoff failure code/message—are cloned and sanitized before recursive freezing, so projection does not freeze or alias caller-owned objects. It contains no raw mutation handle and is never persisted or cached as authority. Renderers receive only this graph.

The normal view answers:

1. the objective and current activity;
2. projected workflow state;
3. progress;
4. why attention is or is not required;
5. one bounded next human action.

Normal output omits session IDs, digests, Runner IDs and latch generations. Technical disclosure is secondary:

- CLI: `aio plan --technical` for plan identity;
- Pi: `/aio status technical` and `/aio plan technical`.

The Pi technical status retains repository/worktree, Git branch and HEAD, task/revision/digest, current/next item, Runner/session/model/reasoning, latch state/generation, handoff ID/state, context percentage/threshold, the top-level runtime condition, and bounded exact nested runtime failure code/message when safely observable. A condition such as `CONTINUITY_FAILED` therefore does not mask a durable root cause such as `REQUIRED_LOCAL_PATH_MISSING`.

## CLI/TUI parity

Canonical correspondence is:

| CLI | Pi |
|---|---|
| `aio status` | `/aio` or `/aio status` |
| `aio why` | `/aio why` |
| `aio next` | `/aio next` |
| `aio plan` | `/aio plan` |
| `aio plan --technical` | `/aio plan technical` |
| — | `/aio status technical` |

For one logical observation, both surfaces consume the same projection fields. Objective, current activity, progress, state, reason and next action therefore cannot diverge through separate business rules. TUI live latch/handoff/session/context facts are additional observations, not contradictory replacements. `aio plan --raw` and `aio plan --check` retain their accepted specialized behavior.

Invalid `TASK_PLAN.md`, repository initialization guidance, non-quiescent runtime and runtime read failures map to the same projected state/reason/next semantics. `why` explains only deterministic system state; it does not invoke or expose model reasoning. `next` is guidance, never an authority-routing decision.

## Guided handoff

The Context Handoff Advisor keeps its fixed configured threshold and one-advisory-per-above-threshold period. Threshold crossing is advisory only.

When the threshold is reached, Pi asks whether to prepare a new session. A negative, closed or failed confirmation invokes no handoff use case and performs no handoff mutation. An affirmative answer invokes exactly once the same `GuardianRunner.handoffFromCommand(ctx, "confirm")` boundary used by `/aio handoff confirm`. The extension no longer inserts a command string with `setEditorText()` or asks the user to press Enter.

The UI layer does not copy handoff logic. The existing path remains:

```text
explicit preparation consent
  -> GuardianRunner command adapter
  -> HandoffService
  -> SafePointCoordinator / AdmissionGate / latch
  -> replacement session created paused
  -> Runner ownership and continuity checks
  -> separate explicit resume confirmation
  -> one admitted resume
```

The in-memory UI guard deduplicates concurrent advisor callbacks. It is not persistent authority or a Human Action Broker. Before displaying the preparation prompt it captures an ephemeral eligibility identity from the coherent authoritative observation: task ID, accepted plan revision and content digest; stable session ID and Runner instance ID; latch state, generation and reason; and the current relevant handoff identity/state or explicit none. Display strings and context percentage are excluded. After human YES, the UI freshly compares those dimensions, the session-shutdown epoch and admission state. Movement at that check stops before the Runner call and produces no retry or second prompt.

The successful UI check is only defense in depth. The exact same invocation-local identity is passed explicitly to the guided `GuardianRunner.handoffFromCommand()` call. Guided callers cannot omit it. Runner validates and captures the approved source object, session ID and Runner instance, then supplies an invocation-local current-source attestation to `HandoffService`; the service rejects malformed identities and revalidates plan, latch and handoff state before any handoff mutation. An accepted HUMAN owner-gate transition is handled specially: the approved pre-transition plan is checked first, `satisfyOwnerGate()` performs the authorized deterministic transition, and the remainder of that handoff is bound to the exact post-transition revision/digest.

After SafePoint drains, the trusted layer checks the captured source again and acquires the existing plan-writer coordination only for the bounded final plan read and reservation interval. A compliant `PlanPort` writer therefore either completes before that final check (and makes consent stale) or fails to acquire the plan lock while reservation is being formed. This does not claim atomicity against arbitrary hostile filesystem rewriting. The identity is not persisted and remains a precondition, not a new authority. ABA detection is limited to accepted authority semantics: latch generation detects latch ABA, while accepted plan revision/content digest bind plan content; no invented global sequence or impossible byte-history guarantee is claimed.

## Consent, takeover and resume

There is no automatic handoff. Context percentage never engages the latch, creates a target, commits handoff state, switches session or sends a resume prompt without affirmative preparation consent.

There is no automatic resume. The replacement remains paused through ownership and continuity checks. The existing separate resume confirmation remains required. Declining it leaves `RESUME_READY`, the latch engaged and zero resume authorization/admission. Affirming it uses the existing exactly-once admission/dispatch path.

Human takeover has hard priority. SafePoint conditionally acquires the latch against the exact observed state/generation/reason in one SQLite transaction. It refuses an existing `HUMAN_TAKEOVER`, never downgrades one, and re-reads the canonical latch after `abort()`, `waitForIdle()`, `waitForNoStreams()` and immediately before returning. The final identity must still be `ENGAGED`, at the acquired generation and with the acquired non-takeover reason.

Durable handoff reservation is the arbitration point. In the same SQLite transaction that inserts a handoff row and active source, reservation requires the exact SafePoint latch identity, rejects `HUMAN_TAKEOVER`, and requires the expected latest handoff identity. Takeover that wins before reservation therefore creates zero handoff row, active source, checkpoint or replacement attempt. If takeover wins after reservation, the existing durable handoff is marked with exact failure evidence; a fresh latch check immediately before replacement prevents `newSession` from starting. This uses no process-global lock and adds no cancellation state machine.

Manual compatibility remains available through `/aio handoff`, `/aio handoff manual`, `/aio handoff recover <handoff-id>`, `/aio takeover` and `/aio resume`.

## Failure and recovery UX

Known failures preserve exact technical identity. Human guidance distinguishes invalid plan, runtime non-quiescence/change/read failure, takeover/latch pause, continuity failure, failed/ambiguous handoff and resume-dispatch ambiguity. `PLAN_CHANGED_DURING_READ` specifically means the authority moved during observation: it requests a fresh observation after the change completes and does not claim plan corruption or prescribe manual repair. Genuine schema/parse/Ledger failures retain `plan --check`, raw inspection and repair guidance.

- `CONTINUITY_FAILED` directs the human to the existing explicit recovery command from a fresh Runner source.
- `HANDOFF_FAILED` and artifact/replacement failures require inspection and manual reconciliation; no hidden target or retry is created.
- `RESUME_DISPATCH_UNKNOWN` explicitly forbids blind redispatch.
- guided handoff errors show what happened, a bounded next action and the original code, and state that no automatic retry occurs.

Manual recovery instructions from the accepted handoff state machine remain visible in technical status.

## Authority and trust model

| Component | Role |
|---|---|
| `TASK_PLAN.md` | Sole current plan authority |
| GuardianStorage | Runtime, latch, handoff, admission and dispatch records for their accepted domains |
| Runner/session | Live runtime observation and Pi host |
| Shared Human Workflow Projection | Read-only derived interpretation; no decision or mutation capability |
| CLI/TUI renderers | Presentation only |
| Guided handoff UI | Explicit human-intent adapter to the existing Runner command use case |
| Ephemeral guided eligibility identity | Invocation-local trusted precondition; never persisted or authoritative |
| `HandoffService` | Handoff mutation/state-machine authority and final consent revalidation |
| `SafePointCoordinator` / `AdmissionGate` | Conditional latch acquisition, safe-point and transport admission authority |

Display strings are never authority. Projection cannot decide completion, alter `TASK_PLAN.md`, create a plan proposal, engage or release a latch, authorize resume, create a replacement session or dispatch work.

## Read-only and model-call guarantees

`status`, `why`, `next` and `plan` perform only observation, projection and formatting. Repeated CLI and Pi integration tests compare plan bytes, runtime mutation counters, journal/handoff counts and latch generation before/after. They create no proposal evidence, plan history, apply attempt, handoff, lock, latch transition, replacement session or plan mutation.

Projection and rendering make zero provider/model calls. The actual Pi SDK command test executes all four `/aio` projections with an offline provider installed and observes zero calls/network attempts.

## Exclusions

0.2-E does not implement:

- 0.2-F durable stop/resume, `STOPPED`, suspend journals or cross-process resume tokens;
- 0.2-G Human Action Broker, question/block queues or generic unblock protocol;
- 0.2-H completion/acceptance inference or a DONE wizard;
- 0.2-I `PROPOSE`/`ESCALATE`/`DEFER` authority routing;
- 0.2-J `MANUAL`/`GUIDED`/`AUTO` autonomy modes;
- `/aio start`, autonomous plan execution or a planner loop;
- a provider, router, external authority dependency or second state store.

Accepted 0.2-B/C/D contracts remain unchanged. In particular, `aio start <objective>` still performs one immutable observation, at most one planner call, strict candidate validation, preview, two-phase TTY authorization, controlled apply and STOP.
