# Aiopago 0.2-E — Unified Interactive Human UX

## Status and purpose

0.2-E unifies the deterministic human workflow shown by the external CLI and the Pi interactive extension. It does not add authority. One immutable, recomputed `aiopago.human-workflow-projection/0.2-e` view now supplies state, severity, headline, objective, current activity, progress, reason, one bounded next action, plan summary, runtime summary, human-control state, handoff guidance and optional technical diagnostics.

```text
authoritative/read-only observations
              |
              v
     projectHumanWorkflow()
          /          \
         v            v
 CLI presenters    Pi presenters
 status/why/next   /aio status/why/next
 plan              /aio plan
```

`formatGuardianStatus()` remains only as a compatibility technical presenter over that projection. It no longer independently decides state, reason or next action.

## Observation adapters

Two read environments feed the same projector:

- `observeHumanWorkflow()` discovers repository configuration, reads `TASK_PLAN.md`, and uses the conservative external runtime reader. It does not instantiate a Runner. External runtime absence, presence without a canonical verifier, concurrent SQLite sidecars, change during read and read failure remain explicitly unavailable or unverified; none becomes a healthy runtime claim.
- `observeRunnerHumanWorkflow()` reads the same plan authority and selected live Runner facts: session identity/model, latch, latest handoff, Git and context use. It exposes no storage, session manager, writer, service or callback. It compares plan, session, latch and handoff identity across the read and reports `RUNTIME_CHANGED_DURING_READ` rather than combining incompatible facts.

The live adapter is additive. It does not replace `TASK_PLAN.md`, GuardianStorage or Runner state with a view model. Both adapters preserve precise diagnostics where available. A verified live claim also carries an explicit task/revision/digest binding and must pass `validateRuntimeObservation()` before any positive projection: coherent live workflow/condition, session and Runner identities, latch state/generation/reason, optional handoff identity/state/failure, and bounded context/Git evidence. Missing, malformed, unknown, contradictory or task-mismatched verified evidence becomes `NEEDS_ATTENTION` with `RUNTIME_OBSERVATION_INVALID`. Explicitly unavailable/unverified external observations retain their conservative supported shape and do not require a live session identity.

## Projection and presentation

The projection is a detached, recursively frozen plain data graph. Selected nested diagnostics—including handoff failure code/message—are cloned and sanitized before recursive freezing, so projection does not freeze or alias caller-owned objects. It contains no raw mutation handle and is never persisted or cached as authority. Renderers receive only this graph.

The normal view answers:

1. the objective and current activity;
2. projected workflow state;
3. progress;
4. why attention is or is not required;
5. one bounded next human action.

Normal output omits session IDs, digests, Runner IDs and latch generations. Technical disclosure is secondary:

- CLI: `aio plan --technical` for plan identity;
- Pi: `/aio status technical` and `/aio plan technical`.

The Pi technical status retains repository/worktree, Git branch and HEAD, task/revision/digest, current/next item, Runner/session/model/reasoning, latch state/generation, handoff ID/state, context percentage/threshold, the top-level runtime condition, and bounded exact nested runtime failure code/message when safely observable. A condition such as `CONTINUITY_FAILED` therefore does not mask a durable root cause such as `REQUIRED_LOCAL_PATH_MISSING`.

## CLI/TUI parity

Canonical correspondence is:

| CLI | Pi |
|---|---|
| `aio status` | `/aio` or `/aio status` |
| `aio why` | `/aio why` |
| `aio next` | `/aio next` |
| `aio plan` | `/aio plan` |
| `aio plan --technical` | `/aio plan technical` |
| — | `/aio status technical` |

For one logical observation, both surfaces consume the same projection fields. Objective, current activity, progress, state, reason and next action therefore cannot diverge through separate business rules. TUI live latch/handoff/session/context facts are additional observations, not contradictory replacements. `aio plan --raw` and `aio plan --check` retain their accepted specialized behavior.

Invalid `TASK_PLAN.md`, repository initialization guidance, non-quiescent runtime and runtime read failures map to the same projected state/reason/next semantics. `why` explains only deterministic system state; it does not invoke or expose model reasoning. `next` is guidance, never an authority-routing decision.

## Guided handoff

The Context Handoff Advisor keeps its fixed configured threshold and one-advisory-per-above-threshold period. Threshold crossing is advisory only.

When the threshold is reached, Pi asks whether to prepare a new session. A negative, closed or failed confirmation invokes no handoff use case and performs no handoff mutation. An affirmative answer invokes exactly once the same `GuardianRunner.handoffFromCommand(ctx, "confirm")` boundary used by `/aio handoff confirm`. The extension no longer inserts a command string with `setEditorText()` or asks the user to press Enter.

The UI layer does not copy handoff logic. The existing path remains:

```text
explicit preparation consent
  -> GuardianRunner command adapter
  -> HandoffService
  -> SafePointCoordinator / AdmissionGate / latch
  -> replacement session created paused
  -> Runner ownership and continuity checks
  -> separate explicit resume confirmation
  -> one admitted resume
```

The in-memory UI guard deduplicates concurrent advisor callbacks. It is not persistent authority or a Human Action Broker. Before displaying the preparation prompt it captures an ephemeral eligibility identity from the coherent authoritative observation: task ID, accepted plan revision and content digest; stable session ID and Runner instance ID; latch state, generation and reason; and the current relevant handoff identity/state or explicit none. Display strings and context percentage are excluded. After human YES, the UI freshly compares those dimensions, the session-shutdown epoch and admission state. Movement at that check stops before the Runner call and produces no retry or second prompt.

The successful UI check is only defense in depth. The exact same invocation-local identity is passed explicitly to the guided `GuardianRunner.handoffFromCommand()` call. Guided callers cannot omit it. Runner validates and captures the approved source object, session ID, Runner instance and Runner-owned lifecycle epoch/ACTIVE state, then supplies an invocation-local current-source attestation to `HandoffService`; the service rejects malformed identities and revalidates plan, latch and handoff state before any handoff mutation. A matching Pi `session_shutdown` invalidates that epoch even if `runtime.session` still points to the same object and ID. The Pi 0.83.x event has no session ID in the event payload, so Runner binds the event through `ctx.sessionManager.getSessionId()`; an unrelated identified session event does not invalidate the captured source. A shutdown/start with the same ID advances the epoch and cannot recreate the old attestation.

Before an accepted HUMAN owner-gate transition, every optional UI/test preparation await has completed. The trusted service then freshly requires the exact registered Runner verifier to attest the same source object, session ID, Runner identity, ACTIVE lifecycle state and lifecycle epoch. A caller-supplied lookalike verifier is not authority. There is no await or other continuation point between this final source attestation and the specialized owner capability.

That capability acquires exact P1 `PlanRevisionWriter` coordination and synchronously asks package-private GuardianStorage authority to prove the exact latch identity with no `HUMAN_TAKEOVER`, exact latest handoff and task eligibility. Task eligibility reuses `taskOperationDisposition()` / `taskOperationBlocksNewHandoff()`: active, crash-stalled, ambiguous and recovery-required ownership rejects before plan bytes, revision, gate, mtime or plan history can change. The check still runs when the owner gate is absent or already satisfied. The SQLite check and deterministic transition contain no await, Promise callback, UI, provider/network operation or SafePoint.

The accepted transition is then CAS-bound to the approved pre-transition task/revision/content digest inside the same `PlanRevisionWriter.commit()` lock. The fresh P1 attestation, task eligibility check and deterministic HUMAN P1→P1' mutation share one bounded cooperative boundary. If a compliant task-operation reservation, SafePoint latch claim, takeover or P2 writer has already won, owner-gate mutation fails closed; if P1' wins, a competing trusted lifecycle creator, takeover or external plan writer cannot enter the check→mutation interval and must freshly attest P1' or fail its stale CAS. An absent or already satisfied gate performs no write but still checks exact P1 and task ownership. The rest of the invocation carries the exact immutable selected P1' (or unchanged P1) snapshot rather than rereading semantic plan fields.

The sequence is therefore `task eligibility → exact owner-gate transition → SafePoint → final reservation arbitration`. Final transactional source arbitration, task-operation arbitration, latest-handoff CAS, latch identity and plan attestation remain mandatory; the pre-mutation check does not replace or weaken them. No plan lock spans SafePoint. If an eligible owner transition finishes and a separate legitimate P1'-bound operation wins afterward, existing latest-handoff/final reservation arbitration admits only one lifecycle; owner-gate satisfaction remains task-level human authority rather than durable operation-specific consent.

After SafePoint drains, the trusted layer checks the captured source lifecycle again and invokes a package-private bounded plan-attestation/reservation capability. It verifies exact P* and performs the conditional SQLite reservation while the short existing plan-writer coordination is held. A compliant `PlanPort` writer therefore either completes before that final check (and makes consent stale) or fails to acquire the plan lock while reservation is being formed. No lock spans owner confirmation or SafePoint waits. `TaskLedger` exposes no arbitrary coordination callback, and neither `PlanRevisionWriter` nor the internal capability is exported through the package root/subpaths. This does not claim global atomicity beyond the shared cooperative `PlanRevisionWriter` and synchronous SQLite model, and does not cover arbitrary hostile filesystem rewriting. The consent identity is not persisted and remains a precondition, not a new authority. ABA detection is limited to accepted authority semantics: latch generation detects latch ABA, Runner lifecycle epoch detects session lifecycle ABA, and accepted plan revision/content digest bind plan content; no invented global sequence or impossible byte-history guarantee is claimed.

Durable reservation carries a detached, recursively frozen selected plan snapshot containing every semantic field needed by checkpoint, manifest and resume prompt construction. The snapshot is persisted inside the existing handoff projection and checkpoint/manifest provenance, not in a second plan store. Checkpoint and manifest construction use only that reserved snapshot and structurally require task/revision/digest/requirements and duplicated semantics to agree. Current `TASK_PLAN.md` may legitimately advance to P2 after reservation; continuity compares P2 with reserved P1 and may fail closed, but P2 cannot contaminate already built P1 artifacts.

## Consent, takeover and resume

There is no automatic handoff. Context percentage never engages the latch, creates a target, commits handoff state, switches session or sends a resume prompt without affirmative preparation consent.

There is no automatic resume. The replacement remains paused through ownership and continuity checks. The separate resume confirmation remains required. Before displaying that prompt, the trusted service creates one immutable invocation-local Resume Expectation E* over the exact handoff and `RESUME_READY` projection, canonical plan semantics and digest, Git identity, target session/file and current Runner lifecycle, runtime/header/durable binding, model/reasoning, idle/no-history state, checkpoint/manifest/prompt identities, required paths, latch generation/reason, empty authorization/admission/dispatch state and current task-operation ownership. E* is not persisted, transferable, or reusable authority; human YES authorizes only that operation. Declining leaves the existing `RESUME_READY` evidence and latch unchanged with zero authorization/admission/dispatch.

After YES, every confirmation path (`/aio resume`, paused-handoff completion and existing-handoff confirmation) converges on the same final Resume Attestation U*. It synchronously re-observes every E* dimension. Canonical P1 attestation, U* capture and SQLite authorization/admission run under the narrow package-private `PlanRevisionWriter` coordination; no plan lock spans the UI prompt or provider send. The same SQLite transaction revalidates exact `RESUME_READY` handoff projection, P1 semantic digest, target/Runner/binding ACTIVE identity, artifact/prompt IDs and digests, latch identity, empty competing resume evidence and latest task-operation owner before releasing the latch and inserting authorization/admission. Runtime ownership and Git remain external synchronous checks immediately adjacent to that transaction: this closes the prompt gap for cooperative plan writers but does not claim global atomicity against privileged arbitrary filesystem writes. Direct `HandoffService.resume()` or public storage admission without the invocation-local trusted inputs fails closed.

Human takeover has hard priority with a defined winner. Its tiny canonical latch acquisition uses the same package-private `PlanRevisionWriter → SQLite authority transaction` order as owner confirmation, trusted SafePoint acquisition, reservation and recovery. If takeover acquires that order first, owner confirmation observes `HUMAN_TAKEOVER` and P1→P1′ cannot commit. If the bounded owner section acquires it first, takeover waits/fails conservatively until P1′ has committed, then may engage. No plan lock spans abort, queue drain, UI, provider calls or `waitForIdle`/`waitForNoStreams`.

After the coordinated latch claim, SafePoint refuses an existing `HUMAN_TAKEOVER`, never downgrades one, and re-reads the canonical latch after `abort()`, `waitForIdle()`, `waitForNoStreams()` and immediately before returning. The final identity must still be `ENGAGED`, at the acquired generation and with the acquired reason.

Durable handoff reservation is the arbitration point. In the same SQLite transaction that inserts a handoff row and active source, reservation requires the exact SafePoint latch identity, rejects `HUMAN_TAKEOVER`, and requires the expected latest handoff identity. An existing active source is returned only when its stable reservation identity—handoff/source/task/revision/digest/latch/Runner/recovery and artifact IDs—is exactly the requested operation; cross-task or different-provenance reuse throws `HANDOFF_ACTIVE_SOURCE_CONFLICT`. Takeover that wins before reservation therefore creates zero handoff row, active source, checkpoint or replacement attempt. If takeover wins after reservation, the existing durable handoff is marked with exact failure evidence; a fresh latch check immediately before replacement prevents `newSession` from starting. This uses no process-global lock and adds no cancellation state machine.

Manual compatibility remains available through `/aio handoff`, `/aio handoff manual`, `/aio handoff recover <handoff-id>`, `/aio takeover` and `/aio resume`.

## Failure and recovery UX

Known failures preserve exact technical identity. Human guidance distinguishes invalid plan, runtime non-quiescence/change/read failure, takeover/latch pause, continuity failure, failed/ambiguous handoff and resume-dispatch ambiguity. `PLAN_CHANGED_DURING_READ` specifically means the authority moved during observation: it requests a fresh observation after the change completes and does not claim plan corruption or prescribe manual repair. Genuine schema/parse/Ledger failures retain `plan --check`, raw inspection and repair guidance.

- `CONTINUITY_FAILED` directs the human to the existing explicit recovery command from a fresh Runner source. Its initial validation and SafePoint are not final authorization. After SafePoint, one detached, recursively frozen invocation-local Recovery Attestation R* freshly proves both **temporal coherence** and **semantic coherence**. Temporal coherence covers the same Runner/source object/session ID and ACTIVE lifecycle epoch; zero conversation history and idle/quiescent queue/retry/compaction/stream state; current Git identity; fresh artifact verification; exact latch state/generation/reason; and unchanged failed handoff plus ACTIVE binding.

  Semantic coherence has one internal canonical normalized P1 projection. It preserves ordered arrays, exact scalars/nulls and canonical required-local-path normalization, and derives a SHA-256 digest with the existing canonical serializer only as consistency evidence—`TASK_PLAN.md` and its content digest remain plan authority. The coordinated Ledger P1, failed top-level plan/model provenance, complete `failed.reserved_plan_snapshot`, checkpoint and manifest must equal that projection for every behavior-critical field they duplicate. Checkpoint completion criteria are compared through their `{ criterion, status: "IN_PROGRESS" }` representation; tests, decisions, task position, plan identity, Git state and lineage are exact. Manifest objective, position, decisions/tests/evidence, minimal reads, required paths, model/reasoning, flattened Git state, source/replacement/Runner binding, session/parent lineage and checkpoint link are exact. Legacy 1.0 evidence may omit its schema-absent required-path field, but any field it represents must still agree. A cryptographically valid artifact envelope/content digest is necessary but is not recovery authority by itself.

  Final plan attestation uses the same package-private `PlanRevisionWriter` coordination accepted for handoff reservation. No plan lock spans SafePoint or another await. While that short lock is held, R* capture, SQLite failed-binding preparation and recovery-child reservation are synchronous; preparation and child reservation share one SQLite transaction. Before its first mutation SQLite recomputes and compares the durable failed reserved-snapshot semantic digest with R*, defending against semantic movement after final capture. The child projection is formed only from R*'s canonical P1/G1/M1/reasoning/latch/source values and normalized reserved plan snapshot; old failed artifacts authorize lineage but do not supply child plan semantics. Later P2/G2/M2 cannot be adopted as recovery provenance. There is no async hook, UI, provider, model or network call between final capture and this durable boundary. Rejection leaves the failed binding ACTIVE and writes neither binding-supersede nor recovery-start/child records. This is the accepted cooperative plan-writer and synchronous JS/SQLite guarantee; it does not claim global atomicity against arbitrary privileged filesystem mutation across Git/artifact files and SQLite.
- One durable task-operation disposition governs generic reservation. `SAFE_TO_HANDOFF` through dispatch-in-flight states are blocking; `CONTINUITY_FAILED` requires explicit recovery; `HANDOFF_FAILED`, artifact/ownership persistence failures, `HUMAN_DECISION_REQUIRED` and dispatch-unknown/failed outcomes require reconciliation. A different source session cannot bypass this with manual, explicit or guided handoff. Source-level uniqueness and latest-handoff consent CAS remain additional independent protections.
- Explicit continuity recovery atomically supersedes the failed ACTIVE binding, journals recovery start and reserves exactly one child, transferring task-operation ownership. A later child may itself reach `CONTINUITY_FAILED` and be explicitly transferred to the next generation; normal F1→C1→C2 recovery therefore remains supported.
- `CHECKPOINT_PERSIST_FAILED`, `RUNNER_OWNERSHIP_ATTESTATION_FAILED` and `MANIFEST_PERSIST_FAILED` persist bounded failure code/message and manual-recovery guidance. Crash-stalled intents such as `CHECKPOINT_PERSISTING`, `REPLACEMENT_SESSION_CREATING` and `MANIFEST_PERSISTING` observed under a different Runner are projected as unknown outcome requiring manual reconciliation—not indefinite “wait”. Reads do not mutate or reconcile them.
- `HANDOFF_FAILED` and artifact/replacement failures require inspection and manual reconciliation; no hidden target or retry is created.
- `RESUME_DISPATCH_UNKNOWN` explicitly forbids blind redispatch and blocks a second task lifecycle.
- guided handoff errors show what happened, a bounded next action and the original code, and state that no automatic retry occurs.

Manual recovery instructions from the accepted handoff state machine remain visible in technical status.

## Authority and trust model

| Component | Role |
|---|---|
| `TASK_PLAN.md` | Sole current plan authority |
| GuardianStorage | Internal runtime, latch, handoff, admission and dispatch authority; no root-exported raw reservation/SQLite writer |
| Runner/session | Live runtime observation and Pi host |
| Shared Human Workflow Projection | Read-only derived interpretation; no decision or mutation capability |
| CLI/TUI renderers | Presentation only |
| Guided handoff UI | Explicit human-intent adapter to the existing Runner command use case |
| Ephemeral guided eligibility identity | Invocation-local trusted precondition; never persisted or authoritative |
| `HandoffService` | Handoff mutation/state-machine authority and final consent revalidation |
| `SafePointCoordinator` / `AdmissionGate` | Conditional latch acquisition, safe-point and transport admission authority |

Display strings are never authority. Projection cannot decide completion, alter `TASK_PLAN.md`, create a plan proposal, engage or release a latch, authorize resume, create a replacement session or dispatch work. `TaskLedger` remains publicly usable for read/validation, but has no public `satisfyOwnerGate()` or public writer handle. `GuardianStorage`, its raw SQLite connection and lifecycle mutators are not package-root APIs. The only production `HANDOFF_CONFIRM` mutation and authoritative reservation paths are the package-private capabilities reached by the trusted Runner/HandoffService lifecycle.

## Read-only and model-call guarantees

`status`, `why`, `next` and `plan` perform only observation, projection and formatting. Repeated CLI and Pi integration tests compare plan bytes, runtime mutation counters, journal/handoff counts and latch generation before/after. They create no proposal evidence, plan history, apply attempt, handoff, lock, latch transition, replacement session or plan mutation.

Projection and rendering make zero provider/model calls. The actual Pi SDK command test executes all four `/aio` projections with an offline provider installed and observes zero calls/network attempts.

## Exclusions

0.2-E does not implement:

- 0.2-F durable stop/resume, `STOPPED`, suspend journals or cross-process resume tokens;
- 0.2-G Human Action Broker, question/block queues or generic unblock protocol;
- 0.2-H completion/acceptance inference or a DONE wizard;
- 0.2-I `PROPOSE`/`ESCALATE`/`DEFER` authority routing;
- 0.2-J `MANUAL`/`GUIDED`/`AUTO` autonomy modes;
- `/aio start`, autonomous plan execution or a planner loop;
- a provider, router, external authority dependency or second state store.

Accepted 0.2-B/C/D contracts remain unchanged. In particular, `aio start <objective>` still performs one immutable observation, at most one planner call, strict candidate validation, preview, two-phase TTY authorization, controlled apply and STOP.
