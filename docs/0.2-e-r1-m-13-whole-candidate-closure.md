## R1-C-01 — supported `aio` runtime does not activate the protected authority path

Severity: **HIGH / closure blocker**

### Evidence

The production CLI launch path is:

```text
runCli()
  -> GuardianRunner.create({ repository })
```

`GuardianRunner.create()` intentionally forbids runtime/test dependency injection. Inside `createGuardianRunner()`, `reservationAuthority` is selected through `injectedOption(...)` and can be supplied only when the lexical `sourceTestCreateAuthority` capability is present. That capability is reachable only through source-test support and is physically removed from the packed artifact.

Therefore the supported production call above necessarily obtains:

```text
reservationAuthority = null
latchAuthority       = portableLatchAuthority(project GuardianStorage)
operationAuthority   = portableOperationAuthority(project GuardianStorage)
HandoffService       = portable/project authority path
```

The secure authority branches inside `HandoffService`, `ArtifactStore`, `SafePointCoordinator`, resume and recovery are consequently not selected by the normal `aio` Runner.

Separately, the checked-in Windows P1S host currently requires a test scenario:

```text
scenario.json
schema = aiopago.operation-authority-test-scenario/1
testScope = true
```

and dispatches the fixed scenario frames to `operation-authority-worker.mjs`. The production service source rejects the scenario path when `testScope` is false. The physical oracle therefore proves the OS-isolated authority worker and store, but it is not the same end-to-end runtime used by ordinary `aio` + Pi/TUI.

Repository-wide PR diff inspection found `new ProtectedSqliteOperationAuthority(...)` only in the protected worker and test/oracle code, not in the normal Runner/CLI activation path.

### Security consequence

The R1-M-13 threat model explicitly includes a separate same-user medium-integrity P0 process capable of modifying project-owned state. The normal product Runner still reads project-owned portable latch/operation/handoff state, so that P0 can forge or erase the very project SQLite rows that the protected oracle was designed to remove from canonical authority.

The package hardening successfully prevents imported package code from acquiring privileged in-process writer capabilities, but that is a different property from restart-authentic same-user persistent authority. A fresh sanitized Node child does not give the child a distinct OS security identity and therefore does not make project SQLite canonical against the R1-M-13 P0 attacker.

Consequently the following prior whole-candidate statement is not yet established for the supported product path:

```text
zero unresolved P0-forgeable canonical authority edges
```

It is established for the isolated protected authority oracle and for semantic tests that explicitly inject the protected authority, but the two evidence halves are not yet composed in one supported runtime.

## Why this is a composition finding, not a reopened domain

The seven protected domains can remain PASS individually. Their state machines do not need to be redesigned merely because activation is missing.

The missing boundary is:

```text
supported interactive runtime
          |
          X   missing authenticated/isolated authority activation
          |
P1S/P2 protected canonical authority
```

Changing operation, latch, reservation, lifecycle, resume, artifact, or recovery semantics without first solving that bridge would add risk without addressing the finding.

## Required remediation gate

Before whole-candidate developer closure can become CLEAN, one of the following must be explicitly accepted and evidenced.

### Path A — compose the secure runtime (preferred under the current R1-M-13 threat model)

Provide a production-supported activation path in which the real interactive Aiopago/Pi workflow uses the same distinct-identity protected authority, with all of these properties:

1. the protected authority is selected by the normal supported runtime, not by source-test injection;
2. P0 cannot mint the capability merely by importing package code, editing project files/SQLite, changing environment variables, or launching an arbitrary sibling process;
3. the production P1S path is not `testScope`/`scenario.json` driven;
4. no generic semantic RPC, arbitrary SQL, eval, module loader, generic Runner/storage method, or broad mutation endpoint is introduced;
5. current exact operation/latch/handoff/lifecycle/resume/recovery state machines remain authoritative and unchanged unless a concrete integration requirement proves otherwise;
6. failure to establish the protected authority fails closed and never falls back to project SQLite;
7. the complete real `aio` + Pi/TUI flow is exercised under the distinct OS identity, including takeover, handoff, paused target, resume, dispatch ambiguity and recovery;
8. restart/crash and P0 project forgery are rerun on that exact integrated path;
9. package/source activation attacks are rerun against the same integrated path;
10. portable/dev mode, if retained, is explicitly labelled non-canonical for the R1-M-13 threat model and cannot be mistaken for secure production evidence.

### Path B — narrow the threat model by a new explicit architecture decision

If same-user P0 resistance is no longer required for 0.2-E, record that as a new reviewed ADR and remove/qualify every production/security claim that depends on R1-M-13 distinct-identity authority. This review does not make that governance decision implicitly.
