1. protected operation authority;
2. protected latch / HUMAN_TAKEOVER authority;

4. protected lifecycle / Runner-session binding authority;
5. protected resume authorization / admission / dispatch authority;

It then traced the actual product path across:

```text

  -> dist/cli-entry.mjs
```

The individual authority state machines, transaction boundaries, fail-closed recovery rules, protected artifact relationships, and package/API confinement remain internally coherent under their selected authority. No migrated domain is reopened by this finding.

## R1-C-01 — supported `aio` runtime does not activate the protected authority path

Severity under the expanded R1-M-13 same-user attacker: **HIGH**.

### Evidence

The normal CLI launch path is:

```text
runCli()
  -> GuardianRunner.create({ repository })
```

`GuardianRunner.create()` intentionally forbids runtime/test dependency injection. Inside `createGuardianRunner()`, `reservationAuthority` is selected through `injectedOption(...)` and can be supplied only when the lexical `sourceTestCreateAuthority` capability is present. That capability is reachable only through source-test support and is physically removed from the packed artifact.

Therefore the supported normal call above necessarily obtains:

```text
reservationAuthority = null
latchAuthority       = portableLatchAuthority(project GuardianStorage)
operationAuthority   = portableOperationAuthority(project GuardianStorage)
HandoffService       = portable/project authority path
```

The protected authority branches inside `HandoffService`, `ArtifactStore`, `SafePointCoordinator`, resume and recovery are consequently not selected by the normal `aio` Runner.

Separately, the checked-in Windows P1S host currently requires a test scenario:

```text
scenario.json
schema = aiopago.operation-authority-test-scenario/1
testScope = true
```

and dispatches the fixed scenario frames to `operation-authority-worker.mjs`. The physical oracle therefore proves the OS-isolated authority worker and store, but it is not the same end-to-end runtime used by ordinary `aio` + Pi/TUI.

Repository-wide PR diff inspection found `new ProtectedSqliteOperationAuthority(...)` only in the protected worker and test/oracle code, not in the normal Runner/CLI activation path.

### Consequence under the R1-M-13 attacker

R1-M-13 explicitly allowed a separate same-user medium-integrity P0 process to modify project-owned state. The normal Runner still uses project-owned portable latch/operation/handoff state, so that attacker can forge or erase those bytes.

Package hardening prevents supported package consumers from acquiring privileged in-process writer capabilities, but that is different from restart-authentic same-user OS isolation. A fresh sanitized Node child does not create a distinct security identity.

Consequently the old unqualified statement:

```text
zero unresolved P0-forgeable canonical authority edges
```

is established only for the protected oracle/injected SECURE state-machine evidence. It is **not** an accurate claim for the normal PORTABLE `aio` path.

## Why this is a profile/deployment finding, not a reopened state-machine domain

The seven protected domains can remain PASS individually. Their state machines do not need redesign merely because the product activation boundary is different.

The missing SECURE boundary is:

```text
normal PORTABLE interactive runtime
          |
          X   no OS-isolated activation
          |
P1S/P2 protected canonical authority
```

Changing operation, latch, reservation, lifecycle, resume, artifact, or recovery semantics without first deciding the deployment profile would add risk without addressing the root cause.

## Architecture evidence after the finding

ADR-0015 and the M0 contracts were re-read during closure.

They freeze **application-level authority by data type**—for example Guardian SQLite as canonical runtime state with deterministic transition-service ownership, fail-closed reads and no generic bidirectional synchronization. They do **not** contain a promise that an arbitrary hostile process under the same OS account cannot directly open/replace the backing SQLite/files.

Issue #30 likewise says 0.2-E unifies human UX and must **preserve existing authority/latch/handoff semantics**; it does not request a new privileged service/native deployment. `docs/0.2-e-unified-human-ux.md` itself begins by stating that 0.2-E **does not add authority**.

The earlier R1-M-13 feasibility spike independently concluded that an OS-authenticated service can provide the stronger property but changes the deployment contract and is incompatible with a bounded npm-first 0.2-E patch.

## Proposed resolution — ADR-0024

`docs/adr/0024-runtime-authority-deployment-profiles.md` is now the explicit decision record required by the original Path B.

It proposes two profiles:

```text
PORTABLE
  application-level ADR-0015 authority
  same-user direct storage/process tamper resistance: not claimed
  target profile for the 0.2 sequence

SECURE
  OS-isolated persistent runtime authority
  same-user hostile P0 resistance required
  production activation not yet implemented
  tracked in issue #46
```

This avoids two false choices:

- pretending the service oracle is already the ordinary `aio` runtime;
- silently turning a UX slice into a privileged multi-platform installer/runtime architecture.

The protected R1-M-13 work is preserved as SECURE-profile evidence rather than discarded.

## Gate before closure can be rerun

R1-C-01 is not closed merely by writing ADR-0024. Before the developer gate can become CLEAN:

1. ADR-0024 must be reviewed/accepted or rejected explicitly;
2. if accepted, normal PORTABLE documentation/README/status claims must stop implying OS-isolated same-user resistance;
3. SECURE documents/oracles must state that production activation is not implemented and point to #46;
4. no normal PORTABLE runtime may display a `SECURE` claim merely because protected code exists in the repository;
5. application-level race/idempotency/consent/handoff semantics from the reviewed candidate must remain green;
6. package/API confinement remains required as a supported-interface boundary, even though package-private JavaScript is not treated as a cryptographic boundary against arbitrary same-user code;
7. whole-candidate tests and the complete supported Pi profile must be rerun;
8. only then may the separate two-round independent acceptance gate start from 0/2.

If ADR-0024 is rejected and SECURE is instead made mandatory for 0.2-E, the original Path A production secure-runtime activation requirements remain fully blocking.

## Additional closure observations

No separate blocker was found in the reviewed composition for:

- operation/latch transaction ordering;
- reservation/latest/source arbitration;
- lifecycle incarnation and supersession;
- resume YES/admission/dispatch-intent atomicity;
- UNKNOWN/DISPATCHING no-replay semantics;

They must be re-reviewed under #46 before any SECURE IPC/activation surface is productized.
