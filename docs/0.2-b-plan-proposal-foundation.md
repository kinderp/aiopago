# Aiopago 0.2-B — Plan Proposal Foundation

## Scope and authority

0.2-B provides an internal, deterministic foundation for structured plan proposals. It does not expose an intent adapter or new CLI/TUI commands, parse natural language, call a model/provider, implement `aio start`, or add a Core Observation Port.

The authoritative Master Task Ledger remains the versioned Markdown `TASK_PLAN.md`. SQLite is not a plan authority. Files under `.guardian/plan-proposals/` are immutable derived provenance and recovery records; they never correct or replace the Markdown source.

## Internal contracts

`PlanProposal` uses schema `aiopago.plan-proposal/0.1.0` and has exactly:

- `schema`, opaque `proposal_id`, and `task_id`;
- exact `base_plan_revision_id` and SHA-256 `base_content_digest` of the observed Markdown bytes;
- new `proposed_plan_revision_id`;
- `requirements_version`, canonical UTC `created_at`, bounded `producer`, and `change_reason`;
- a complete structured `candidate_plan`.

The proposal has no goal/prompt/model fields. Construction clones, validates, digests, and deeply freezes its payload. The candidate must use the proposal task, requirements version, new revision, and timestamp. The proposal digest is SHA-256 over canonical JSON; no meaning is inferred from an ID prefix.

A successful apply returns immutable `aiopago.plan-apply-result/0.1.0`. It includes proposal/task identity, previous/new revisions and byte digests, `applied_at`, the structured diff, provenance, and its repository-relative reference.

The concrete `aiopago.plan-revision/0.1.0` provenance record contains:

- `plan_revision_id`, `task_id`, and `previous_revision_id`;
- `requirements_version` and exact resulting `content_digest`;
- `created_at`, `producer`, and `change_reason`;
- `authority: DERIVED_PROVENANCE`.

`approved_by` is absent unless a future real approval event supplies it; 0.2-B invents no approval.

## One Plan Port write boundary

`PlanRevisionWriter` is the only `TASK_PLAN.md` filesystem replacement boundary. It performs cooperative serialization, initial attestation, candidate validation, final attestation, temporary exclusive creation, write, file `fsync`, close, atomic replacement, best-effort directory `fsync`, and deterministic normal-path cleanup.

Both `PlanPort.apply()` and the existing `TaskLedger.satisfyOwnerGate()` delegate to this primitive. The owner-gate operation remains a specialized handoff mutation with its prior exact-command canonicalization, human actor requirement, lifecycle guards, and revision semantics; it is not converted into a public Plan Proposal.

## Validation and materialization

`validateTaskLedger()` is the extracted canonical implementation used by `TaskLedger.validate()`, reads, owner-gate mutation, proposal construction, preview, and apply. There is no second Ledger validator. It retains schema/status/required-field checks, path bounds, DAG dependency and cycle checks, DONE evidence, sole `IN_PROGRESS`, current/next lifecycle, and owner-gate-relevant validation performed by the specialized mutation.

Materialization is offline and provider-neutral. It starts from the exact observed bytes, validates the canonical metadata, and changes only:

- `**Current revision:**`;
- `**Requirements version:**`;
- `**Updated:**`;
- the JSON `task-ledger` block.

The JSON object keys are rendered in sorted order while array order remains proposal data. The source line-ending convention is retained for LF and CRLF. Prose, comments, whitespace, and sections outside the normative metadata/JSON regions remain byte-for-byte unchanged. The returned digest is SHA-256 of the exact candidate Markdown bytes.

Canonical mutation requires one `aiopago.task-ledger/0.1.0` header and synchronized metadata. Read compatibility does not trigger migration or rewriting.

## Compare-and-swap and concurrency

Apply requires both current `plan_revision_id == base_plan_revision_id` and current byte digest `== base_content_digest`. Revision-only, digest-only, or combined mismatch returns `PLAN_CAS_CONFLICT`; there is no merge, last-write-wins, reload/retry, or semantic-equivalence exception. A caller must observe again and create a new proposal.

Every cooperative Aiopago writer atomically creates `.guardian/plan-write.lock`. Contention, stale lock, or corrupt lock fails immediately with `PLAN_WRITE_LOCKED`; there is no wait or automatic stale-lock deletion. Cleanup is deterministic after a completed process path. This uses Node filesystem primitives supported on Windows.

The writer attests the base after acquiring the lock, materializes, then reads and attests it again immediately before replacement. This serializes and makes all Aiopago plan writers CAS-safe. An uncooperative human editor can still write between the final read and filesystem rename; ordinary rename APIs do not provide an atomic compare-and-replace against arbitrary external writers. 0.2-B therefore does not claim protection beyond cooperative writers plus the narrow final-attestation window.

## Proposal identity, provenance, and recovery

The path `.guardian/plan-proposals/<opaque-derived-record-id>/` contains immutable records:

1. `prepared.json` is linked into place without overwrite before plan replacement;
2. `applied.json` is linked into place without overwrite after replacement.

A proposal ID already registered with another proposal digest fails with `PLAN_PROPOSAL_ID_CONFLICT`. The same ID and payload returns the original apply result when the current Markdown matches it. It cannot generate a second revision, including after process restart.

If replacement fails, `prepared.json` is a non-authoritative recovery record and the original plan remains unchanged. A same-payload retry may continue only while the exact base still matches. If replacement committed but `applied.json` did not, apply reports `PLAN_APPLY_COMMITTED_PROVENANCE_PENDING`; retry recognizes the exact candidate revision/digest and completes the immutable applied record without another plan write. Any other state fails closed as a CAS or recovery conflict. Temporary files are never authoritative.

## Diff

`aiopago.plan-diff/0.1.0` separates `added`, `removed`, and `changed` values for top-level plan fields and task items. Task items use `task_item_id` identity. Field and item output is lexically ordered and independent of object insertion order. Values are structural only: no SQLite/runtime/session data, private reasoning, or inferred semantics is included.

A candidate cannot be a revision no-op: reusing the base revision is rejected with `PLAN_REVISION_REUSE`. A valid candidate therefore records at least the revision transition in the plan diff.

## Legacy policy

Reading the exact pre-rename Ledger schema remains supported, and all 0.2-A views remain read-only with no silent migration. Plan Proposal mutation of `eiopago.task-ledger/0.1.0` is rejected with `PLAN_LEGACY_MIGRATION_REQUIRED`. The historical root Ledger is not a mutation/dogfood target. The pre-existing owner-gate compatibility path remains supported because changing it would regress an already deployed handoff contract; this exception does not authorize general legacy Plan Proposal mutation.

## Exclusions and next boundary

0.2-B has no user-facing `plan propose`, `plan diff`, or `plan apply` command and no public intent contract. `plan.observe`, `plan.propose`, `plan.validate`, `plan.diff`, and `plan.apply` adapter semantics belong exclusively to 0.2-C. Planning providers, natural-language intent, Core Observation Port, start/stop, and runtime authority changes remain out of scope.
