# Aiopago 0.2-B — Plan Proposal Foundation remediation

## Status and scope

0.2-B is **READY FOR INDEPENDENT REVIEW** after Independent Review Round 1 remediation; acceptance gate is **0/2**. It is not CLOSED. 0.2-C is NOT STARTED and remains blocked until 0.2-B is accepted.

This slice is an internal, deterministic structured-plan foundation only. It adds no Intent Adapter, natural-language planning, provider/LLM call, `aio start`, mutating CLI/TUI command, or Core Observation Port. The 0.2-A commands (`status`, `why`, `next`, `plan`, `plan --raw`, `plan --check`, `plan --technical`) remain read-only and do not acquire the plan lock or create proposal/history state.

`TASK_PLAN.md` Markdown remains the only current plan authority. SQLite and every file below `.guardian/plan-proposals/` or `.guardian/plan-history/` are derived evidence; they cannot correct, replace, or independently prove the current authority.

## Strict JSON domain and proposal identity

`strictJsonClone()` is the single recursive trust-boundary canonicalizer. It accepts only null, booleans, strings, finite numbers, dense arrays, and plain objects. It rejects undefined, non-finite numbers, bigint, symbol, function, Date/Map/Set/RegExp, ArrayBuffer and views, class/custom-prototype objects, accessors, hidden/extra array properties, symbol keys, cycles, and excessive depth/size. `-0` is normalized to `0`.

`PlanProposal` (`aiopago.plan-proposal/0.1.0`) creates one canonical JSON clone before semantic validation. Proposal digest, deep freeze, materialization, and diff all derive from that representation. Mutation of the caller's original graph after construction cannot alter any reachable proposal payload or digest.

The proposal contains exactly its opaque identity, task/base revision, exact SHA-256 base-byte digest, proposed revision, requirements version, canonical creation timestamp, producer/reason, and complete candidate Ledger. It has no prompt, goal, model, provider, or private reasoning field.

## Ledger validation

`validateTaskLedger()` is the general mutation gate and validates the strict JSON domain plus the M0 Task/TaskItem contract. It checks all required Task and TaskItem fields, bounded non-empty IDs/text, canonical RFC3339 UTC timestamps, status vocabulary, criteria/evidence/reference arrays, risk/milestone/actor strings, exact item task identity, unique item IDs and dependencies, known dependency IDs, DAG cycles, DONE evidence, at most one IN_PROGRESS item, and current/next lifecycle consistency. Optional/unknown compatible fields remain allowed only when they are strict JSON values.

## Single controlled writer and final CAS ordering

`PlanRevisionWriter.commit()` is the only authority-replacement boundary used by both Plan Proposal apply and `TaskLedger.satisfyOwnerGate()`. There is no public `atomicReplace` or equivalent raw replacement method. A commit requires a semantic validator and always performs owned lock acquisition, exact byte/revision observation, candidate validation, history persistence, final CAS, final lock attestation, and one rename.

The order is:

1. acquire and retain an owned lock file descriptor;
2. read/validate the exact base bytes and revision;
3. materialize and validate the candidate;
4. exclusively create the candidate temp, preserve portable mode, write, fsync, capture filesystem identity, close;
5. durably preserve the exact content-addressed base snapshot;
6. durably publish proposal registration and commit intent/witness;
7. perform the final authoritative observation and exact revision+byte-digest CAS;
8. attest final lock path identity and ownership token;
9. immediately rename the already-prepared temp over `TASK_PLAN.md`;
10. perform directory sync and post-commit evidence bookkeeping.

No serialization, candidate/provenance write, fsync, history operation, callback, or temp preparation occurs between the final authority read/CAS and rename. The only operations in that interval are the required final lock identity/token attestation and the rename syscall.

A portable filesystem API still cannot atomically compare arbitrary current bytes and rename against a non-cooperative editor. The exact residual race is therefore: **completion of the final authority read/CAS → bounded final lock path/identity/token attestation → entry into the rename syscall**. A non-cooperative editor can write anywhere in that interval; no candidate, history, or provenance preparation remains there. The lock attestation must follow CAS to prove writer ownership at commit. Cooperative Aiopago writers share the lock, and no automatic retry hides a conflict.

## Lock ownership

The lock record contains a cryptographically random 256-bit ownership token. Its descriptor stays open for the operation, and device/inode identity is captured from `fstat`. Before rename, the writer reopens the path without following a trusted provenance assumption and requires regular/non-symlink/single-link status, canonical realpath, matching filesystem identity, and exact token bytes. Missing, replaced, hardlinked, or modified locks fail before rename.

Release repeats the identity/token attestation and unlinks only the acquired lock. If writer A's lock path was removed or replaced by writer B, A neither commits nor removes B's lock. Stale/corrupt locks still require explicit human inspection; there is no timeout or automatic stale deletion.

## Exact revision history

Before every replacement, the writer exclusively persists exact base bytes at:

`.guardian/plan-history/sha256-<base-hex>.md`

The path is bound to the SHA-256 digest. Existing content is accepted only if the exact bytes and digest match; redirects, unexpected hardlinks, or different bytes fail closed. File and directory durability are requested before final CAS. `PlanRevision` (`aiopago.plan-revision/0.2.0`) records previous revision ID, previous content digest, and previous snapshot reference. History is derived and never current authority; Aiopago does not create a Git commit without explicit policy.

## Provenance, commit witness, and timestamp truth

The proposal record directory contains:

- immutable `proposal.json`: exact proposal payload and digest;
- immutable `attempts/<random-256-bit-token>.json`: a versioned COMMIT_INTENT;
- immutable `applied.json`: apply/recovery result.

Every trusted read requires canonical real paths, real parent directories, regular non-symlink files, expected single-link count, bounded size, strict JSON domain, and exact closed schema. More importantly, records are never authority. Recovery reloads the exact base snapshot and deterministically recomputes the candidate Ledger, exact candidate Markdown bytes/digest, diff, and all static PlanRevision/result fields from the caller proposal.

A commit intent records proposal/base identity, candidate digest, exact base and candidate-temp filesystem identities, random attempt token, history reference, deterministic diff/PlanRevision, and `prepared_at`. Rename preserves the prepared temp identity on supported Windows and POSIX local filesystems. Recovery requires the current authority to have both exact candidate bytes/digest/semantics and the committed temp's filesystem identity, distinct from the base identity. An external in-place write of coincidentally equal candidate bytes retains the base identity and yields `PLAN_RECOVERY_AMBIGUOUS`, never success.

Normal `aiopago.plan-apply-result/0.2.0` writes `applied_at` only after rename and has `recovered_at=null`. If rename is witnessed after a crash but no durable post-commit result preserved the instant, recovery reports `applied_at=null` and sets `recovered_at` to actual recovery time. `prepared_at` is never reused as a claimed apply time.

The witness distinguishes normal/cooperative editor effects, not a malicious same-account administrator able to rewrite all local files and records. That attacker is outside this local trust model.

## Recovery matrix

| State | Result |
|---|---|
| A. proposal registered, no temp, base unchanged | safe retry |
| B. candidate prepared, base unchanged, no rename | safe retry; normal-path temp cleanup |
| C. history persisted, base unchanged | safe retry after exact history verification |
| D. commit intent persisted, base unchanged | safe retry; never treated as applied |
| E. rename occurred, applied missing, witness matches | deterministic recovery; truthful null `applied_at` if exact instant was not durable |
| F. current exact candidate, witness missing/mismatched | `PLAN_RECOVERY_AMBIGUOUS` |
| G. unrelated newer authority | recovery/CAS conflict |
| H. applied record differs from deterministic candidate | provenance invalid |
| I. proposal/provenance path is redirected or symlinked | reject |
| J. same proposal ID with another digest | `PLAN_PROPOSAL_ID_CONFLICT` |

No recovery path derives success merely from current digest or provenance files.

## Materialization, metadata, and owner gate

Materialization updates only the three normative metadata lines and the deterministic JSON Ledger block. It preserves prose and bytes outside those regions and retains LF/CRLF convention. Candidate digest is over exact materialized Markdown bytes.

On POSIX, the prepared temp receives the authority's permission mode before fsync/rename; normal same-process ownership is naturally retained. Node's portable API cannot atomically preserve arbitrary ACLs, Windows extended attributes, or every platform-specific metadata stream during replacement. This remains a documented residual LOW; security metadata is not weakened deliberately to imitate unsupported attributes.

`satisfyOwnerGate()` remains the specialized HUMAN-only `HANDOFF_CONFIRM` transition with the same authorization, BLOCKED→SATISFIED lifecycle, revision, item, next-step, idempotency, and concurrency semantics. It uses the same owned CAS writer, prepared-temp ordering, exact history, and metadata policy. Legacy pre-rename read/owner-gate compatibility for `eiopago.task-ledger/0.1.0` remains; general Plan Proposal mutation still requires the canonical Aiopago Ledger schema.

## Platform semantics

On POSIX and Windows local filesystems, Node rename of the prepared file preserves the file object identity observed through device/inode-equivalent `stat` fields; tests verify the recovery witness on the supported Windows environment, while POSIX mode preservation is conditionally tested on POSIX. Directory fsync remains best-effort because Windows and some filesystems do not expose a portable durable-directory primitive through Node. Network/virtual filesystems that do not provide stable identity or atomic same-filesystem rename fail witness verification or remain outside the supported guarantee.
