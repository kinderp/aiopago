# Aiopago 0.2-B — Plan Proposal Foundation remediation

## Status and scope

0.2-B is **READY FOR INDEPENDENT REVIEW** after Independent Review Round 1 remediation; acceptance gate is **0/2**. It is not CLOSED. 0.2-C is NOT STARTED and remains blocked until 0.2-B is accepted.

This slice is an internal, deterministic structured-plan foundation only. The independent `docs/efficiency-benchmark-requirement.md` remains base documentation and is not implemented here. This slice adds no Efficiency Benchmark, Intent Adapter, natural-language planning, provider/LLM call, `aio start`, mutating CLI/TUI command, or Core Observation Port. The 0.2-A commands (`status`, `why`, `next`, `plan`, `plan --raw`, `plan --check`, `plan --technical`) remain read-only and do not acquire the plan lock or create proposal/history state.

`TASK_PLAN.md` Markdown remains the only current plan authority. SQLite and every file below `.guardian/plan-proposals/` or `.guardian/plan-history/` are derived evidence; they cannot correct, replace, or independently prove the current authority.

## Strict JSON domain and proposal identity

`strictJsonClone()` is the single recursive trust-boundary canonicalizer. It accepts only null, booleans, strings, finite numbers, dense arrays, and plain objects. It rejects undefined, non-finite numbers, bigint, symbol, function, Date/Map/Set/RegExp, ArrayBuffer and views, class/custom-prototype objects, accessors, hidden/extra array properties, symbol keys, cycles, and excessive depth/size. `-0` is normalized to `0`.

`PlanProposal` (`aiopago.plan-proposal/0.1.0`) creates one canonical JSON clone before semantic validation. Proposal digest, deep freeze, materialization, and diff all derive from that representation. Mutation of the caller's original graph after construction cannot alter any reachable proposal payload or digest. `PlanPort.proposal()` always extracts own enumerable data descriptors for the canonical proposal fields and constructs a fresh `PlanProposal`; it never trusts `instanceof`, subclasses, modified prototypes, or a caller-provided `proposal_digest`.

The proposal contains exactly its opaque identity, task/base revision, exact SHA-256 base-byte digest, proposed revision, requirements version, canonical creation timestamp, producer/reason, and complete candidate Ledger. It has no prompt, goal, model, provider, or private reasoning field. Proposal registrations are independently capped at 64 MiB; diff records at 96 MiB; commit records at 128 MiB. These evidence limits are distinct from the 32 MiB `TASK_PLAN.md` authority limit.

## Ledger validation

`validateTaskLedger()` is the general mutation gate and validates the strict JSON domain plus the M0 Task/TaskItem contract. It checks all required Task and TaskItem fields, bounded non-empty IDs/text, canonical RFC3339 UTC timestamps, status vocabulary, criteria/evidence/reference arrays, risk/milestone/actor strings, exact item task identity, unique item IDs and dependencies, known dependency IDs, DAG cycles, DONE evidence, at most one IN_PROGRESS item, and current/next lifecycle consistency. Optional/unknown compatible fields remain allowed only when they are strict JSON values.

`DROPPED` and `SUPERSEDED` Tasks and TaskItems require the bounded canonical fields `terminal_reason`, `terminal_actor`, and `terminal_at`. A `SUPERSEDED` TaskItem additionally requires `superseded_by` to name another existing TaskItem; that replacement must reciprocally name it through `supersedes`. Both directions reject unknown IDs, self-reference, missing reciprocity, and contradictory replacement relationships. This is terminal provenance only and adds no 0.2-H completion/acceptance semantics.

## Single controlled writer and final CAS ordering

`PlanRevisionWriter.commit()` is the only authority-replacement boundary used by both Plan Proposal apply and `TaskLedger.satisfyOwnerGate()`. There is no public `atomicReplace` or equivalent raw replacement method. A commit requires a semantic validator and always performs owned lock acquisition, exact byte/revision observation, candidate validation, history persistence, final lock attestation, final CAS, and one rename.

The order is:

1. acquire and retain an owned lock file descriptor;
2. read/validate the exact base bytes and revision;
3. materialize and validate the candidate;
4. exclusively create the candidate temp, preserve portable mode, write, fsync, capture filesystem identity, close;
5. durably preserve the exact content-addressed base snapshot;
6. durably publish proposal registration and commit intent/witness;
7. attest final lock path identity and ownership token;
8. perform the final authoritative observation and exact revision+byte-digest CAS;
9. immediately invoke rename on the already-prepared temp over `TASK_PLAN.md`;
10. perform directory sync and post-commit evidence bookkeeping.

No lock read, callback, serialization, candidate/provenance I/O, fsync, history operation, or other filesystem operation occurs between completion of the final authoritative observation/CAS and rename. Only in-memory comparisons and the irreducible user-space-to-rename-syscall transition remain. An adversarial test mutates `TASK_PLAN.md` while lock attestation reads; because attestation now precedes the final authority observation, that observation detects the edit.

A portable filesystem API still cannot combine comparison of arbitrary current bytes and rename into one kernel primitive. A non-cooperative editor could therefore write in the irreducible transition after the final observation and before kernel entry. Cooperative Aiopago writers share the owned lock, and no automatic retry hides a conflict.

## Lock ownership

The lock record contains a cryptographically random 256-bit ownership token. Its descriptor stays open for the operation, and device/inode identity is captured from `fstat`. Before rename, the writer reopens the path without following a trusted provenance assumption and requires regular/non-symlink/single-link status, canonical realpath, matching filesystem identity, and exact token bytes. Missing, replaced, hardlinked, or modified locks fail before rename.

Release repeats the identity/token attestation and unlinks only the acquired lock. If writer A's lock path was removed or replaced by writer B, A neither commits nor removes B's lock. Stale/corrupt locks still require explicit human inspection; there is no timeout or automatic stale deletion.

## Exact revision history

Before every replacement, the writer exclusively persists exact base bytes at:

`.guardian/plan-history/sha256-<base-hex>.md`

The path is bound to the SHA-256 digest. Existing content is accepted only if the exact bytes and digest match; redirects, unexpected hardlinks, or different bytes fail closed. File and directory durability are requested before final CAS. `PlanRevision` (`aiopago.plan-revision/0.2.0`) records previous revision ID, previous content digest, and previous snapshot reference. History is derived and never current authority; Aiopago does not create a Git commit without explicit policy.

## Provenance, commit witness, and timestamp truth

The proposal record directory contains:

- immutable `proposal.json`: exact proposal payload and digest;
- immutable `attempts/<random-256-bit-token>.json`: a versioned COMMIT_INTENT;
- immutable `applied.json`: live post-rename apply result.

Every trusted read requires canonical real paths, real parent directories, regular non-symlink files, expected single-link count, bounded size, strict JSON domain, and exact closed schema. More importantly, records are never authority. Inspection reloads the exact base snapshot and deterministically recomputes the candidate Ledger, exact candidate Markdown bytes/digest, diff, and all static PlanRevision/result fields from the caller proposal.

A commit intent records proposal/base identity, candidate digest, exact base and candidate-temp filesystem identities, random attempt token, history reference, deterministic diff/PlanRevision, and `prepared_at`. Rename preserves the prepared temp identity on supported Windows and POSIX local filesystems. That identity proves which file object became authority, not which actor renamed it.

Accordingly, 0.2-B is fail-closed: exact candidate authority without an already durable `applied.json` is always `PLAN_RECOVERY_AMBIGUOUS`, even when an intent's temp identity matches. Aiopago does not create `applied.json`, `applied_at`, or a recovered-success result during retry. This includes external write/copy, external rename of an orphan Aiopago temp, and the genuine crash window after rename but before result publication. Manual reconciliation or a new explicitly authorized plan revision is required.

A normal uninterrupted `aiopago.plan-apply-result/0.2.0` writes the actual post-rename `applied_at` and keeps `recovered_at=null`. A trustworthy existing result plus the exact candidate authority and matching commit witness remains idempotent. `prepared_at` is never reused as a claimed apply time.

## Recovery matrix

| State | Result |
|---|---|
| A. proposal registered, no temp, base unchanged | safe retry |
| B. candidate prepared, base unchanged, no rename | safe retry; normal-path temp cleanup |
| C. history persisted, base unchanged | safe retry after exact history verification |
| D. commit intent persisted, base unchanged | safe retry; never treated as applied |
| E. current exact candidate, applied missing (witness matches or not) | `PLAN_RECOVERY_AMBIGUOUS`; manual reconciliation |
| F. current exact candidate, trustworthy applied result and matching witness | idempotent success |
| G. unrelated newer authority | recovery/CAS conflict |
| H. applied record differs from deterministic candidate | provenance invalid |
| I. proposal/provenance path is redirected or symlinked | reject |
| J. same proposal ID with another digest | `PLAN_PROPOSAL_ID_CONFLICT` |

No retry derives success from witness identity, current digest, or an intent. Only the durable result produced by the live post-rename execution supports idempotent success. A proposal has at most 128 durable intents: at capacity, existing result inspection still runs, while an unapplied base fails with `PLAN_ATTEMPT_LIMIT_REACHED` and explicit `ABANDON_PROPOSAL` disposition. Reconciliation and a new proposal ID are required rather than accidental attempt 129.

## Materialization, metadata, and owner gate

Materialization updates only the three normative metadata lines and the deterministic JSON Ledger block. It preserves prose and bytes outside those regions and retains LF/CRLF convention. Candidate digest is over exact materialized Markdown bytes. All authority reads use fatal UTF-8 validation before Markdown/JSON parsing; malformed bytes, including invalid bytes in unrelated prose, fail closed. Valid Unicode and an optional UTF-8 BOM are accepted and preserved. Candidate authority size is checked against the reader's shared 32 MiB limit before temp creation, history/intent publication, or replacement.

On POSIX, the prepared temp receives the authority's permission mode before fsync/rename; normal same-process ownership is naturally retained. Node's portable API cannot atomically preserve arbitrary ACLs, Windows extended attributes, or every platform-specific metadata stream during replacement. This remains a documented residual LOW; security metadata is not weakened deliberately to imitate unsupported attributes.

`satisfyOwnerGate()` remains the specialized HUMAN-only `HANDOFF_CONFIRM` transition with the same authorization, BLOCKED→SATISFIED lifecycle, revision, item, next-step, idempotency, and concurrency semantics. A generic `PlanProposal` must preserve an existing `owner_gate` exactly under canonical strict JSON comparison and may not introduce one when absent; delete, forged satisfaction, command/item changes, and `satisfied_by` changes are rejected. Only the specialized path may transition it. It uses the same owned CAS writer, prepared-temp ordering, exact history, and metadata policy. Legacy pre-rename read/owner-gate compatibility for `eiopago.task-ledger/0.1.0` remains; general Plan Proposal mutation still requires the canonical Aiopago Ledger schema.

## Platform semantics

On POSIX and Windows local filesystems, Node rename of the prepared file preserves the file object identity observed through device/inode-equivalent `stat` fields; tests verify the witness on the supported Windows environment, while POSIX mode preservation is conditionally tested on POSIX. Directory open/fsync/close failures surface unless the platform/error explicitly reports an unsupported directory-sync primitive (`ENOTSUP`, `EOPNOTSUPP`, `ENOSYS`; on Windows, open `EPERM`/`EINVAL`/`EISDIR` or fsync `EPERM`/`EINVAL`/`EBADF`). Only those cases are best effort. Exact byte consistency from atomic rename is distinct from power-loss durability, which requires supported successful directory fsync. Network/virtual filesystems without stable identity or atomic same-filesystem rename remain outside the supported guarantee.
