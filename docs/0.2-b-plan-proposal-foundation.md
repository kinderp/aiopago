# Aiopago 0.2-B — Plan Proposal Foundation remediation

## Status and scope

0.2-B is **READY FOR INDEPENDENT REVIEW** after Independent Review Round 1 remediation; acceptance gate is **0/2**. It is not CLOSED. 0.2-C is NOT STARTED and remains blocked until 0.2-B is accepted.

This slice is an internal, deterministic structured-plan foundation only. The independent `docs/efficiency-benchmark-requirement.md` remains base documentation and is not implemented here. This slice adds no Efficiency Benchmark, Intent Adapter, natural-language planning, provider/LLM call, `aio start`, mutating CLI/TUI command, or Core Observation Port. The 0.2-A commands (`status`, `why`, `next`, `plan`, `plan --raw`, `plan --check`, `plan --technical`) remain read-only and do not acquire the plan lock or create proposal/history state.

`TASK_PLAN.md` Markdown remains the only current plan authority. SQLite and every file below `.guardian/plan-proposals/` or `.guardian/plan-history/` are derived evidence; they cannot correct, replace, or independently prove the current authority.

## Strict JSON domain and proposal identity

`strictJsonClone()` is the single recursive trust-boundary canonicalizer. It accepts only null, booleans, strings, finite numbers, dense arrays, and plain objects. It rejects undefined, non-finite numbers, bigint, symbol, function, Date/Map/Set/RegExp, ArrayBuffer and views, class/custom-prototype objects, accessors, hidden/extra array properties, symbol keys, cycles, and excessive depth/size. `-0` is normalized to `0`.

`PlanProposal` (`aiopago.plan-proposal/0.1.0`) creates one canonical JSON clone before semantic validation. Proposal digest, deep freeze, materialization, and diff all derive from that representation. Mutation of the caller's original graph after construction cannot alter any reachable proposal payload or digest. `PlanPort.proposal()` always extracts own enumerable data descriptors for the canonical proposal fields and constructs a fresh `PlanProposal`; it never trusts `instanceof`, subclasses, modified prototypes, or a caller-provided `proposal_digest`.

The proposal contains exactly its opaque identity, task/base revision, exact SHA-256 base-byte digest, proposed revision, requirements version, canonical creation timestamp, producer/reason, and complete candidate Ledger. It has no prompt, goal, model, provider, or private reasoning field. Proposal registrations are independently capped at 64 MiB; diff records at 96 MiB; commit records at 128 MiB. These evidence limits are distinct from the 32 MiB `TASK_PLAN.md` authority limit.

## Ledger validation

`validateTaskLedger()` is the general mutation gate and validates the strict JSON domain plus the M0 Task/TaskItem contract. It checks all required Task and TaskItem fields, bounded non-empty IDs/text, canonical RFC3339 UTC timestamps, status vocabulary, criteria/evidence/reference arrays, risk/milestone/actor strings, exact item task identity, unique item IDs and dependencies, known dependency IDs, DAG cycles, DONE evidence, at most one IN_PROGRESS item, and current/next lifecycle consistency. Optional/unknown compatible Task fields remain allowed only when they are strict JSON values.

`owner_gate`, when present in schema 0.1.0, is a closed authorization contract rather than an extension point. The only known kind is `HANDOFF_CONFIRM`, and its command is the closed semantic enum `/aio handoff confirm`; the compatibility spellings `/eio handoff confirm` and `/eiopago handoff confirm` canonicalize to that same fixed operation. Malformed or extended owner commands fail closed rather than becoming authorization authority. The only statuses are `BLOCKED` and `SATISFIED`; unknown kinds, statuses, fields, malformed target data, or unsupported authorization semantics fail closed with `OWNER_GATE_INVALID` and are not silently forward-compatible. A BLOCKED gate contains live lifecycle authority: its protected `item_id` must exist, be BLOCKED, equal `next_item`, and coexist with a BLOCKED task, null current item, and no IN_PROGRESS item. A configured non-null future `satisfied_next_item` must also exist and remain PLANNED or BLOCKED while the gate is BLOCKED.

A SATISFIED gate is historical audit data. Its bounded `item_id` and optional bounded `satisfied_next_item` no longer have to exist in the current TaskItem projection and acquire no requirement about a current item status; exact plan history retains the projection at the transition. Canonical `satisfied_at` and bounded `human:*` `satisfied_by` remain mandatory. The real legacy SATISFIED shape persisted at `b317f79` remains readable through an exact closed audit-only extension set: `evidence_handoff_id`, `post_fix_validation_handoff_id`, and `post_fix_replacement_session_id` are bounded opaque strings, while `post_fix_continuity` and `final_acceptance` accept only the historically observed `PASS` value. These fields are forbidden on BLOCKED gates and cannot affect authorization or lifecycle. Unknown legacy-looking, future, or authorization-like fields still fail closed.

For schema 0.1.0, terminal provenance remains compatible with the base contract rather than standardizing new mandatory spellings. A complete legacy `reason`/`actor`/`timestamp` form or complete `terminal_reason`/`terminal_actor`/`terminal_at` alias form is accepted; if both are present they must agree. Partial, mixed, conflicting, unbounded, or non-canonical provenance fails closed. Existing `supersedes`/`superseded_by` IDs are bounded, non-self, and must reference existing items, but this slice deliberately adds no new reciprocity, cardinality, or supersession-cycle lifecycle policy.

## Single controlled writer and final CAS ordering

`PlanRevisionWriter.commit()` is the only authority-replacement boundary used by both Plan Proposal apply and `TaskLedger.satisfyOwnerGate()`. There is no public `atomicReplace` or equivalent raw replacement method. A commit requires a semantic validator and always performs owned lock acquisition, exact byte/revision observation, candidate validation, history persistence, final lock attestation, final CAS, and one rename.

The order is:

1. preflight-read UTF-8, structure, and semantics without creating `.guardian` state;
2. acquire and retain an owned lock file descriptor, then re-read/validate the exact base bytes and revision;
3. materialize and validate the candidate;
4. exclusively create the candidate temp, preserve portable mode, write, fsync, capture filesystem identity, close;
5. durably preserve the exact content-addressed base snapshot;
6. durably publish proposal registration and commit intent/witness;
7. attest final lock path identity and ownership token;
8. perform a raw final authority snapshot with pre/post descriptor metadata (`identity`, regular-file state, size, link count, nanosecond mtime/ctime where available), close the descriptor, then attest the pathname with `lstat → realpath → final lstat`; both pathname observations must match each other and the descriptor fingerprint, and the snapshot must match the initial exact authority;
9. after only in-memory comparisons, immediately invoke rename on the already-prepared temp over `TASK_PLAN.md`;
10. perform directory sync and post-commit evidence bookkeeping.

No lock read, callback, parsing, serialization, candidate/provenance I/O, timestamp/random operation, fsync, history operation, or other filesystem operation occurs after the final pathname `lstat` and before rename. Only object/primitive comparisons, fail-closed in-memory branches, and the rename invocation remain. Descriptor write-in-place changes and atomic-save, delete/recreate, symlink, hardlink, and swaps on either side of the post-read `realpath` are rejected. The exact residual gap is only completion of the final pathname `lstat` to entry into the rename syscall; a non-cooperative replacement in that irreducible interval remains LOW.

A portable filesystem API still cannot combine comparison of arbitrary current bytes and rename into one kernel primitive. A non-cooperative editor could therefore write in the irreducible transition after the final observation and before kernel entry. Cooperative Aiopago writers share the owned lock, and no automatic retry hides a conflict.

## Lock ownership

The lock record contains a cryptographically random 256-bit ownership token. Its descriptor stays open for the operation, and device/inode identity is captured from `fstat`. Before rename, the writer reopens the path without following a trusted provenance assumption and requires regular/non-symlink/single-link status, canonical realpath, matching filesystem identity, and exact token bytes. Missing, replaced, hardlinked, or modified locks fail before rename.

Release repeats the identity/token attestation and unlinks only the acquired lock. If writer A's lock path was removed or replaced by writer B, A neither commits nor removes B's lock. Stale/corrupt locks still require explicit human inspection; there is no timeout or automatic stale deletion.

## Exact revision history

Before every replacement, the writer exclusively persists exact base bytes at:

`.guardian/plan-history/sha256-<base-hex>.md`

The path is bound to the SHA-256 digest. Existing content is accepted only if the exact bytes and digest match; redirects, unexpected hardlinks, or different bytes fail closed. File and directory durability are requested before final CAS. `PlanRevision` (`aiopago.plan-revision/0.2.0`) records previous revision ID, previous content digest, and previous snapshot reference. History is derived and never current authority; Aiopago does not create a Git commit without explicit policy.

## Provenance, commit witness, and timestamp truth

The proposal record directory contains:

- immutable `proposal.json`: exact proposal payload and digest;
- immutable `attempts/<random-256-bit-token>.json`: a versioned COMMIT_INTENT;
- immutable `applied.json`: live post-rename apply result.

Every trusted read requires canonical real paths, real parent directories, regular non-symlink files, expected single-link count, bounded size, strict JSON domain, and exact closed schema. More importantly, records are never authority. Inspection reloads the exact base snapshot and deterministically recomputes the candidate Ledger, exact candidate Markdown bytes/digest, diff, and all static PlanRevision/result fields from the caller proposal.

A commit intent records proposal/base identity, candidate digest, exact base and candidate-temp filesystem identities, random attempt token, history reference, deterministic diff/PlanRevision, and `prepared_at`. Rename preserves the prepared temp identity on supported Windows and POSIX local filesystems. That identity proves which file object became authority, not which actor renamed it.

Accordingly, proposal, intent, applied, history, and filesystem-witness files are derived audit evidence only. They can detect mismatch or tampering, but same-filesystem evidence cannot authenticate the actor. Whenever authority is the exact candidate and the current `PlanPort` instance lacks a private volatile receipt created by its own completed post-rename path, apply returns `PLAN_RECOVERY_AMBIGUOUS` even if `applied.json` and every witness are exact. This includes external write/copy, external rename of an orphan temp, forged exact applied evidence, a genuine crash window, and every process/`PlanPort` restart. Human reconciliation or a new explicitly authorized revision is required.

A normal uninterrupted `aiopago.plan-apply-result/0.2.0` exclusively creates `applied.json` only after rename/readback, writes the actual post-rename `applied_at`, requires `applied_at >= prepared_at`, keeps `recovered_at=null`, and only then installs the in-memory receipt after applied-file and parent-directory durability. Pre-existing applied destinations cannot complete the live path. The private receipt binds proposal digest, attempt token, content digest, exact result, and the committed authority's device/inode, size, link count, mtime, and ctime fingerprint observed after rename. Same-instance idempotent success requires current exact candidate bytes, valid disk audit evidence, and the same filesystem identity/fingerprint. Exact B bytes recreated in a new object after B→C→B, or restored in place after metadata-changing mutation, are ambiguous rather than success. The receipt is never serialized as an authenticator. Clock rollback after commit produces pending/ambiguous state rather than a clamped timestamp. This is a deliberate availability-for-safety tradeoff.

## Recovery matrix

| State | Result |
|---|---|
| A. proposal registered, no temp, base unchanged | safe retry |
| B. candidate prepared, base unchanged, no rename | safe retry; normal-path temp cleanup |
| C. history persisted, base unchanged | safe retry after exact history verification |
| D. commit intent persisted, base unchanged | safe retry; never treated as applied |
| E. current exact candidate, applied missing (witness matches or not) | `PLAN_RECOVERY_AMBIGUOUS`; manual reconciliation |
| F. current exact candidate, exact applied result and matching witness | same-instance success only with matching volatile live receipt; otherwise ambiguous |
| G. unrelated newer authority | recovery/CAS conflict |
| H. applied record differs from deterministic candidate | provenance invalid |
| I. proposal/provenance path is redirected or symlinked | reject |
| J. same proposal ID with another digest | `PLAN_PROPOSAL_ID_CONFLICT` |

No restart retry derives success from witness identity, current digest, intent, or applied disk evidence. Only a matching private receipt in the same `PlanPort` runtime supports idempotent success. A proposal has at most 128 durable intents: at capacity, evidence inspection still runs, while an unapplied base fails with `PLAN_ATTEMPT_LIMIT_REACHED` and explicit `ABANDON_PROPOSAL` disposition. Reconciliation and a new proposal ID are required rather than accidental attempt 129.

## Materialization, metadata, and owner gate

Materialization supports both canonical 0.1.0 layouts: the compact base bootstrap layout has only the schema header plus JSON block, while the extended layout has one coherent copy of all three revision/requirements/updated headers. One internal structural Markdown helper is shared by generic Plan Proposal materialization and the specialized owner-gate writer; it recognizes both `aiopago.task-ledger/0.1.0` and readable `eiopago.task-ledger/0.1.0` layouts without changing either caller's mutation policy. Its line-oriented parser recognizes metadata only in the contiguous structural header region immediately after the unique Schema line. Extended metadata must be exactly the three canonical lines in order and end at the header boundary; partial, duplicate, malformed, or mismatched structural metadata fails closed. Compact files remain compact and replace only the JSON block. Extended files replace the JSON block and update only parser-returned value spans; the owner-gate path changes Current revision and Updated while preserving Requirements version. Metadata-like text after the header boundary—including plain prose, bullets, quotes, and fenced examples—is not metadata and remains byte-identical. LF/CRLF, Unicode, unrelated bytes, and an optional UTF-8 BOM are preserved. Candidate digest is over exact materialized Markdown bytes. All authority reads use fatal UTF-8 validation before Markdown/JSON parsing; malformed bytes, including invalid bytes in unrelated prose, fail before lock/state creation. Candidate authority size is checked against the reader's shared 32 MiB limit before temp creation, history/intent publication, or replacement.

On POSIX, the prepared temp receives the authority's permission mode before fsync/rename; normal same-process ownership is naturally retained. Node's portable API cannot atomically preserve arbitrary ACLs, Windows extended attributes, or every platform-specific metadata stream during replacement. This remains a documented residual LOW; security metadata is not weakened deliberately to imitate unsupported attributes.

`satisfyOwnerGate()` remains the specialized HUMAN-only `HANDOFF_CONFIRM` transition with the same authorization, BLOCKED→SATISFIED lifecycle, revision, item, next-step, idempotency, and concurrency semantics. Before materialization, a transition-specific validator constructs the exact expected candidate from a strict JSON clone of the base, applies only the authorized gate/task/protected-item mutations, and requires canonical-JSON deep equality with the actual candidate. This exact-delta assertion preserves every other Task, TaskItem, owner-gate, extension, item-order, and audit field. `satisfied_task_status` defaults to IN_PROGRESS and, when persisted, may only be IN_PROGRESS. At the transition instant a non-null `satisfied_next_item` must be a different existing PLANNED or BLOCKED item. Authorization canonicalization and lexical slash-command mention scanning both derive from one command-token primitive with JavaScript `/\s/` separator semantics, including line breaks and Unicode whitespace. The `/aio`, `/eio`, and `/eiopago` aliases therefore remain equivalent without allowing an alias or whitespace spelling to repeat the authorization command in `satisfied_next_step`; surrounding Markdown and punctuation are not folded into command tokens.

A generic `PlanProposal` must preserve an existing validated `owner_gate` exactly and may not introduce one. Defense in depth treats every gate not proven known-and-SATISFIED as latched rather than returning on unknown data. While a `HANDOFF_CONFIRM` gate is BLOCKED it must also preserve task status, current/next item, next step, every existing item status, item identity set, dependency/supersession topology, the protected BLOCKED item, and the absence of IN_PROGRESS items. Conservative non-lifecycle prose/criteria/evidence metadata edits remain possible. Only the specialized human path may release the latch. Legacy pre-rename read/owner-gate compatibility for `eiopago.task-ledger/0.1.0` remains; general Plan Proposal mutation still requires the canonical Aiopago Ledger schema.

## Platform semantics

On POSIX and Windows local filesystems, Node rename of the prepared file preserves the file object identity observed through device/inode-equivalent `stat` fields; tests verify the witness on the supported Windows environment, while POSIX mode preservation is conditionally tested on POSIX. Directory open/fsync/close failures surface unless the platform/error explicitly reports an unsupported directory-sync primitive (`ENOTSUP`, `EOPNOTSUPP`, `ENOSYS`; on Windows, open `EPERM`/`EINVAL`/`EISDIR` or fsync `EPERM`/`EINVAL`/`EBADF`). Only those cases are best effort. Exact byte consistency from atomic rename is distinct from power-loss durability, which requires supported successful directory fsync. Network/virtual filesystems without stable identity or atomic same-filesystem rename remain outside the supported guarantee.
