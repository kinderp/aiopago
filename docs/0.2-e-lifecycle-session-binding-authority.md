Starting commit: `d96ae947088b2fc60c4995a4700b70d2fbf52fe5`. PR #31 remains draft. Independent gate remains 0/2. This slice does not start 0.2-F and does not migrate resume authorization/admission/dispatch, recovery, plan authority, or artifact authority.

## Lifecycle taxonomy

Two different mechanisms remain intentionally separate:

- **Invocation-local source lifecycle:** `GuardianRunner` owns the exact current session object, textual session ID, Runner ID, monotonic in-memory epoch and ACTIVE flag. Real Pi `session_start`/`session_shutdown` identity comes from `ctx.sessionManager.getSessionId()`. This is the final synchronous asynchronous-race attestation used before reservation and recovery boundaries. It is not persisted merely for symmetry.
- **Durable session binding authority:** the relation between one protected handoff reservation and its replacement session, Runner, random binding nonce, lifecycle incarnation, `ACTIVE|SUPERSEDED` status and append-only transition provenance. This slice moves that relation into the protected canonical SQLite store.
- **Portable lifecycle:** project `runner_session_bindings` and `RUNNER_SESSION_BOUND` / `RUNNER_SESSION_BINDING_SUPERSEDED` journal rows remain compatibility/dev projections only. They are never selected as secure authority and are labelled accordingly in `authorities`.

## State machine

The repository has exactly two binding states.

| State | Creation / predecessor | Valid successor | Idempotency | Conflict semantics |
|---|---|---|---|---|
| `ACTIVE` | created once after external paused replacement creation, runtime custom-binding verification and exact ACTIVE Runner lifecycle capture; requires matching protected reservation | `SUPERSEDED` | exact create/request replay returns the same row without timestamp rewrite | same handoff/session/binding with changed Runner, binding nonce or incarnation rejects; no last-writer-wins |
| `SUPERSEDED` | only from exact expected `ACTIVE` identity | none (terminal) | exact transition replay returns the same row/event | stale incarnation/Runner/session/binding rejects; different terminal reason conflicts |

`session_shutdown` of the exact current protected target advances the in-memory epoch to inactive and synchronously supersedes the matching canonical ACTIVE binding with reason `session_shutdown`. An unrelated identified session event changes neither memory nor canonical state. A same-textual-ID restart creates a new in-memory epoch but cannot revive the terminal E1 binding. No generic activate, revive, release, delete or arbitrary bind operation exists.

## Protected architecture

Protected schema is `aiopago.operation-authority/1.3.0`; fixed private protocol is `aiopago.operation-authority-protocol/4`. New canonical tables:

- `lifecycle_bindings(handoff_id PK/FK, replacement_session_id UNIQUE, runner_instance_id, session_binding_id UNIQUE, lifecycle_incarnation, status, bound_at, bind_event_id, superseded_at, superseded_reason, supersede_event_id)`;
- `lifecycle_binding_events(sequence, event_id UNIQUE, request_id UNIQUE, exact binding identity, event_type, from_status, status, reason, occurred_at)`.

`authority_requests` remains the shared protected idempotency/conflict ledger. Schema 1.2.0 upgrades one way to 1.3.0; a current store missing or corrupting either lifecycle table fails closed.

Fixed private semantic operations are `LIFECYCLE_BIND_CREATE`, `LIFECYCLE_BIND_GET`, `LIFECYCLE_BIND_GET_SESSION`, `LIFECYCLE_BIND_TRANSITION`, and `LIFECYCLE_BIND_EVENTS`. Create is not an arbitrary `BIND_SESSION`: it requires an existing protected reservation and exact reservation Runner/binding nonce. Transition requires the complete expected binding identity, ACTIVE state, only the legal `SUPERSEDED` successor and a bounded reason. There is no arbitrary SQL, generic storage/Runner method, resume, recovery, admission or dispatch operation.

P1S remains LocalService plus the unique Aiopago service SID. P2 remains the protected Node worker over inherited private pipes. The canonical DB remains `%ProgramData%\Aiopago\OperationAuthority\canonical\operations.sqlite`. Secure failures never select project SQLite.

## Handoff choreography and failure evidence

SQLite cannot atomically create a Pi session. The established choreography is preserved:

1. protected reservation commits;
2. compatibility reservation projection is attempted;
3. checkpoint persists;
4. replacement-create intent is projected;
5. Pi externally creates the paused target and installs its runtime custom binding;
6. HandoffService records the target in project lifecycle evidence;
7. exact runtime binding plus current Runner lifecycle incarnation are verified synchronously;
8. protected binding row/event/request commit atomically;
9. compatibility binding projection is rewritten from canonical proof;
10. manifest/continuity proceed to `RESUME_READY`; secure resume still stops unavailable.

If external replacement creation succeeds but protected binding commit fails, the target remains paused, canonical reservation remains exact, no canonical binding is invented, and project failure/manual-reconciliation evidence is retained. If canonical binding commits but compatibility projection fails, canonical state survives and the operation fails closed; no resume or silent retry occurs.

## Coupling and second reservation

The previous slice rejected every second reservation for a task. This slice permits exactly one established lifecycle transfer: the latest protected reservation must have an ACTIVE binding whose replacement session equals the new source and whose Runner equals the new reservation Runner. Final reservation still checks expected latest digest and the exact source lifecycle. After shutdown/supersession, the old target cannot authorize another reservation. This enables a genuine `S1 → S2 → S3` protected handoff chain without migrating resume or recovery.

## Boundaries retained

- Secure `prepareResumeConfirmation()` and `resume()` still return `SECURE_RESUME_AUTHORITY_UNAVAILABLE`; forged project authorization/admission/dispatch cannot progress the target.
- Secure recovery still returns `SECURE_RECOVERY_AUTHORITY_UNAVAILABLE`; protected lifecycle readability is not recovery authorization.
- Plan revision/digest and artifact IDs remain reservation references, not proof that plan or artifact bytes are authentic.
- M-03 invocation-local source behavior is unchanged. M-06/M-07 portable recovery regressions remain green, but no secure recovery PASS is claimed.
- Protected operation, latch/takeover and handoff reservation/active-source domains remain canonical in the same store.
