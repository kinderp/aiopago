# Aiopago 0.2-D — Start planning from an objective

## Status and purpose

0.2-D is **READY FOR INDEPENDENT REVIEW** in draft PR #28 with independent gate **0/2** after the fresh Independent Review Round 1 on candidate `5f292dcb7aafb0dc5a2196cdf69636692588f396` was blocked by H-01. H-01 and its related lifecycle documentation LOW L-01 are remediated; the earlier Pi settings M-01 remains closed. It adds one bounded vertical slice:

```text
human objective
  -> Pi planning agent
  -> full structured candidate Ledger
  -> accepted 0.2-C plan.propose / validate / diff
  -> explicit human authorization
  -> accepted 0.2-C plan.apply and 0.2-B controlled writer
  -> STOP
```

It plans and, if authorized, creates a plan revision. It does **not** execute that plan or begin implementation.

## Command

Aiopago must already be initialized with `aio init`; `aio start` does not invent a second bootstrap contract.

```bash
aio start "Realizza un server P2P in Python con discovery dei peer e test"
```

For an objective beginning with a hyphen, use the conventional separator:

```bash
aio start -- "-mantieni questa stringa come semplice obiettivo"
```

The objective is one required argv value, accepts Unicode and newlines where the shell permits them, and is limited to 16 KiB of UTF-8. It is data: no `eval`, shell interpolation, command execution, or option interpretation occurs inside Aiopago. Quote objectives containing spaces. `eio start` remains the deprecated executable alias and delegates to the same flow; there is no separate `eiopago` shell executable in the accepted rename compatibility model (`/eiopago` is a TUI command alias).

The command displays the current/proposed revision, proposal ID and digest, and every canonical `PlanDiff` plan/item addition, removal, and changed field. Production stdin authorization is available only from an interactive TTY and has two phases:

```text
Apply this plan? [y/N] yes
Confirm 7K4M2Q8R: 7K4M2Q8R
```

Phase 1 requires exactly one complete, bounded record containing only `y` or `yes`, case-insensitively, terminated by LF or CRLF. Only after that record succeeds does Aiopago generate and display a fresh invocation-local 10-character challenge from a cryptographically secure standard-library random source. Phase 2 requires that exact challenge in a second complete LF/CRLF-terminated bounded record. Neither phase trims whitespace. EOF, blank/other/control/binary/oversized input, bare CR, a wrong or partial challenge, stream errors, and extra bytes already observed after the phase-2 terminator deny.

Both phases use one stream iterator and one pending buffer. Thus a queued terminal paste such as `yes\nno\n` supplies `yes` to phase 1 and `no` to phase 2 and denies, whether the PTY exposes it in one chunk or separate canonical reads. The challenge is generated only after phase 1, so pre-existing input cannot know the production challenge. This boundary rejects already observed trailing input; it does not claim to predict arbitrary future terminal keystrokes.

Piped, redirected, file, CI, or otherwise non-TTY stdin always denies immediately and is not drained as an authorization proof. Automated tests and programmatic callers can inject the existing explicit authorization boundary into `startPlanning()`; this is not a CLI approval capability. Cancellation is a normal exit and prints `Plan not applied.` There is no `--yes`.

After a successful apply, the command reports the applied revision and proposal ID, states that implementation has not started, and exits.

## Layering and planner boundary

```text
CLI parser / renderer
  -> startPlanning use case
     -> ObjectivePlanner.plan({ objective, immutable observation })
     -> 0.2-C adapter
     -> presentation boundary
     -> authorization boundary
     -> exact 0.2-C apply
```

The production `PiObjectivePlanner` reuses the supported Pi 0.83.x SDK and its existing model/auth/settings discovery. It creates one in-memory, no-tools planning session with extensions, skills, prompt templates, themes, and context files disabled. After Pi service/resource initialization performs its settings reload, Aiopago applies invocation-local effective settings to the same manager used by the session: agent retry is disabled with zero retries, provider retry receives `maxRetries: 0`, and compaction is disabled. Runtime getters are attested before session creation. These temporary overrides use `applyOverrides`, are never saved or flushed, and do not rewrite or create project/global Pi settings. Thus one planning attempt makes at most one provider/model call, including retryable provider failures and near-compaction responses.

It uses the configured/default Pi model; no provider router or Aiopago credential store is added. Missing Pi/model/auth/provider configuration fails clearly and safely. Tests inject deterministic planners or an offline fake provider transport; the regression boundary uses the actual resolved Pi 0.83.0 SDK without network access.

The planner receives only the objective and the immutable 0.2-C observation (identity plus current full Ledger). It receives no `PlanPort`, `PlanRevisionWriter`, filesystem mutation, shell, approval token, or apply function. Project/global prompt resources are disabled for this bounded call. The prompt asks for no hidden reasoning.

## Strict output contract

The provider must return exactly one strict JSON object:

```json
{
  "candidate_plan": {
    "schema_version": "0.1.0",
    "task_id": "TASK-...",
    "plan_revision_id": "PLAN-new-revision",
    "task_items": []
  }
}
```

`candidate_plan` is a **full** replacement Ledger, including existing completed work; it is not a patch or prose plan. Markdown fences, prose, comments, multiple roots, duplicate object names, unknown root fields, `NaN`/`Infinity`, malformed JSON, excessive nesting/nodes, and responses over 32 MiB are rejected without repair or retry. The trusted boundary clones into the existing strict JSON domain, rejecting accessors, custom prototypes, symbols, functions, `undefined`, `BigInt`, cycles, sparse/extended arrays, host objects, and non-finite numbers.

The candidate then passes unchanged through accepted Ledger, owner-gate, 0.2-C proposal/materialization, and 32 MiB authority validation. Malformed lifecycle, forged `task_id`, reused revision, invalid requirements value, unknown/cyclic dependency, unsupported `DONE`, or invalid owner gate fails before presentation/authorization. There is no fallback plan and no malformed-output repair.

## Original observed-base binding

One attempt performs exactly one initial observation:

```js
const observation = plan.observe();
const result = await planner.plan({ objective, observation });
const proposal = plan.propose({
  schema: "aiopago.plan-intent/0.1.0",
  proposal_id,
  producer: "aio-start/0.2-d",
  change_reason: "Plan candidate generated by aio start from a human objective.",
  base: {
    task_id: observation.task_id,
    plan_revision_id: observation.plan_revision_id,
    content_digest: observation.content_digest
  },
  candidate_plan: result.candidate_plan
});
```

The original identity is copied automatically. Aiopago never observes again to substitute a fresh base, rebases/merges, retries against a newer authority, or calls the planner again. If authority A moves to C while B is being planned, `plan.propose(B/base A)` surfaces `PLAN_PROPOSAL_STALE`; C remains exact and no approval prompt appears. The user must explicitly restart `aio start` from a fresh observation.

If authority changes after diff/approval but before apply, accepted 0.2-B CAS/lock semantics surface the original conflict (normally `PLAN_CAS_CONFLICT`). Approval never means force apply. Recovery, lock, provenance, attempt-limit, proposal-ID, owner-gate, and ambiguity error identities are not collapsed into a generic start error.

## Authorization and exact-proposal binding

Presentation and authorization receive the same frozen observation/proposal/diff graph. One authorization permits one apply attempt for that exact proposal digest and base in the current invocation. The use case does not regenerate the proposal, proposal ID, candidate, diff, or planner result between display and apply. Therefore:

```text
what the user saw == what the user approved == what plan.apply attempts
```

Authorization defaults to deny and is not persisted as a credential. Only the two complete interactive records defined above can approve. The challenge is generated once per affirmative phase 1, remains only in the authorization invocation, and is never written to `TASK_PLAN.md`, settings, session state, or provenance. Non-TTY input cannot approve at all. Denial/EOF calls no apply and creates no proposal/apply/provenance state; 0.2-C observe/propose/validate/diff remain read-side. There is no `--yes` in this slice.

The general `Apply?` prompt is not the specialized HUMAN `HANDOFF_CONFIRM` transition. A blocked owner latch remains protected by accepted 0.2-B/C rules; a planner cannot remove, rewrite, satisfy, or advance through it.

## Existing plan and source of truth

`aio start` always observes the existing initialized `TASK_PLAN.md`, including active/completed work, and asks the planner for a revision of that authority. It never silently resets an existing project. `TASK_PLAN.md` remains the sole current plan authority. Objective text, provider response, in-memory planning session, proposal, diff, validation, and `.guardian` provenance are not plan authorities. There is no objective file, secondary Markdown plan, planner database, SQLite mirror, last-write-wins, bidirectional synchronization, or durable Intent database.

## Trust table

| Input/component | Trust and capability |
|---|---|
| Human objective | Untrusted user data; bounded argv text only |
| Pi agent/model | Untrusted candidate producer; no tools or mutation capability |
| `plan.observe()` | Trusted current authority snapshot and identity |
| Planner candidate | Untrusted until strict parsing and accepted Ledger/proposal validation |
| Reconstructed 0.2-C `PlanProposal` | Canonical validated structured candidate; still unauthorized |
| Canonical `PlanDiff` | Deterministic informational input to approval |
| Human decision | Permits one exact apply attempt only |
| `plan.apply()` | Delegates mutation to accepted 0.2-B controls |
| `TASK_PLAN.md` | Sole current plan authority |

Objectives and provider output may be malicious. Objective `<`/`>` characters are JSON-escaped before prompt delimiting, and the system contract labels all embedded objective/plan strings as untrusted data. This is defense in depth only: model compliance is never the security boundary. Trusted validation, authorization, and controlled apply are the boundary. Provider secrets, raw responses, objective text, and hidden reasoning are not logged to provenance; the planning session is in-memory and disposed after the single call.

## Examples

New objective on an initialized repository:

```bash
aio start "Realizza un server P2P in Python con discovery dei peer e test"
```

Replanning an existing authority without discarding completed items:

```bash
aio start "Aggiungi autenticazione OAuth al servizio mantenendo i task già completati"
```

Both flows observe the current Ledger, request a full structured revision, show the exact canonical diff, require interactive `y`/`yes` followed by the fresh exact challenge, apply through 0.2-C/0.2-B, and stop without coding.

## Explicit exclusions

0.2-D adds no 0.2-E TUI redesign, autonomous task execution, continuous loop, task runner, implementation branch, shell execution, generic workflow/DSL, issue/GitHub adapter, provider/model router, `--yes`, auto-approval, hidden retry/replan/rebase, raw writer export, shared database, or mandatory FARO/Durex/Raiatea/Alfred dependency. The package root continues to expose only the accepted `plan.*` mutation facade; internal planner modules remain blocked package subpaths.
