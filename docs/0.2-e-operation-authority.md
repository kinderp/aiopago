## Selected boundary

`src/operation-authority.mjs` and `src/protected-operation-authority.mjs` define an explicit replaceable authority interface:

- `PortableOperationAuthority`: delegates to user-owned `GuardianStorage`, labelled `PORTABLE`, non-canonical, and without an R1-M-13 claim.
- `ProtectedSqliteOperationAuthority`: isolated from the ordinary Runner bundle, labelled `SECURE`, canonical, and usable only against an existing protected store unless P1S explicitly authorizes first initialization.
- `requireSecureOperationAuthority()`: rejects a portable object. No catch path selects portable storage after a secure failure.

`ToolOperationTracker` owns unchanged production classification while delegating durable admission/terminal mutation to the selected authority. `SafePointCoordinator` reads that same selected authority. Ordinary npm Runner execution is explicitly portable. Secure execution is P1S-launched P2: it receives no project SQLite as canonical input and opens only the protected operation DB under the service token.

The fixed protocol is `aiopago.operation-authority-protocol/1`. Its mutation vocabulary is `OPERATION_ADMIT_TOOL`, `OPERATION_FINISH_TOOL`, `OPERATION_MARK_UNKNOWN`, and bounded exact retries; reads are `OPERATION_GET` and `OPERATION_LIST_TASK`. There is no eval, arbitrary SQL, module loading, generic GuardianStorage method, callback registration, arbitrary Runner method, or public named pipe. A physical crash operation exists only when both the protected config says test scope and the service name has the scoped test prefix.

Readable JavaScript can reproduce every algorithm and can create a fake database under P0 ownership. It still cannot mutate the exact canonical database: the protected directory grants the unique service SID, SYSTEM, and Administrators, not P0 or shared LocalService. P2 additionally verifies its actual Windows token contains the expected service SID and verifies P1 parent/P2/capability binding on inherited anonymous pipes. Copying the worker and setting its role marker conveys no SID, private channel, key, or canonical DB access.

## Windows foundation

Stable production identity/layout:

```text
service:  AiopagoOperationAuthority
root:     %ProgramData%\Aiopago\OperationAuthority
bin\      broker-service.exe, node.exe, operation-authority-worker.mjs
canonical\identity.bin, operations.sqlite, SQLite WAL/SHM
runtime\  bounded service result/diagnostic state
control\  protected version/hash/service-SID configuration
```

Physical tests use only `AiopagoOperationAuthorityTest-<unique>` and `%ProgramData%\Aiopago\OperationAuthorityTests\<unique>`. The native P1S host is C#/.NET Framework source under `service/windows-operation-authority`; no generated executable is committed. It runs as LocalService with an **UNRESTRICTED** unique service SID, validates LocalService plus that unique SID, validates broker/Node/worker SHA-256 and protocol version, generates the persistent 32-byte identity only after service entry, then launches protected P2 with injection variables stripped. Identity bytes are never logged.

Provisioning creates empty directories, directly installs numeric service-SID DACLs and Administrators ownership, runs a real Explorer-token medium P0 negative probe, then copies binary/configuration, creates the service last, and lets P1S create first secret/DB. It never creates a key or database and hardens it later.

Canonical SQLite uses `journal_mode=WAL`, `synchronous=FULL`, foreign keys, bounded busy timeout, schema/integrity checks, admission and terminal payload digests, and a protected request ledger. The canonical directory DACL also covers `-wal`, `-shm`, temporary files and future sibling backups. Project `.guardian` is never used as secure input.
