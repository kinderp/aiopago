Accepted historical semantics are unchanged:

- initial state is `RELEASED`, generation 0, reason null;
- `RELEASED → ENGAGED` increments generation once;
- ordinary `ENGAGED → HUMAN_TAKEOVER` is a priority escalation at the same generation and changes the exact reason identity;
- duplicate same-reason claim is idempotent and does not rewrite timestamps/actor;
- ordinary claim against `HUMAN_TAKEOVER` is `HUMAN_TAKEOVER_ACTIVE`;
- different ordinary reason is `LATCH_REASON_MISMATCH`;
- expected state/generation/reason mismatch is `LATCH_GENERATION_MISMATCH`;
- no generic release API exists. Historical ordinary release is inseparable from trusted resume authorization/admission, and that domain is deliberately not migrated here. `HUMAN_TAKEOVER` cannot be released by that path. Secure handoff/resume therefore remains fail-closed rather than using portable latch state.

## Architecture

`src/latch-authority.mjs` adds explicit authority labels:

- `PortableLatchAuthority`: delegates reads to ordinary user-owned `GuardianStorage`; non-canonical and compatibility/dev only.
- `ProtectedSqliteOperationAuthority`: now also implements the secure canonical latch interface and carries a separate secure latch label.
- `requireSecureLatchAuthority`: rejects portable state. No catch or fallback selects project SQLite.

Operation and latch tables intentionally share protected `operations.sqlite`. This is not convenience coupling: a new operation admission must validate `RELEASED` and the exact generation in the same `BEGIN IMMEDIATE` transaction that inserts the operation. Separate databases would leave an uncloseable stale-read race or require a broader two-phase protocol.

SafePoint receives an explicit latch authority. In secure mode every reread uses protected state. The ordinary npm Runner remains explicitly portable. P1S launches the protected P2 worker under LocalService plus the unique Aiopago service SID; only its inherited private channel accepts fixed latch operations. There is no named `TAKEOVER` pipe, public semantic RPC, eval, arbitrary SQL, module/function dispatch, or generic release command.

## Canonical schema

Protected schema `aiopago.operation-authority/1.1.0`, protocol `aiopago.operation-authority-protocol/2`:

- `latches(task_id PK, state, generation, reason, engaged_at, engaged_by, released_at, released_by, last_event_id)`;
- `latch_events(sequence PK, event_id UNIQUE, request_id UNIQUE, task_id, event_type, generation, from_reason, reason, actor, occurred_at)`;
- shared `authority_requests(request_id PK, operation_type, payload_digest, result_json, recorded_at)`;
- existing `operations` table unchanged.

Bootstrap, claim/escalation event, latch row, and request result commit together. A crash before COMMIT preserves the previous exact row and event/request set. Exact request replay returns the recorded result; changed payload under one request ID returns `LATCH_REQUEST_CONFLICT`. Current-schema missing latch tables fail closed; the sole accepted upgrade is 1.0.0 → 1.1.0.

## Admission/takeover ordering

| Takeover order | Admission order | Expected result | Durable result |
|---|---|---|---|
| takeover commits first | admission second | admission refused | takeover `ENGAGED/HUMAN_TAKEOVER`; no operation |
| admission commits first | takeover second | admitted atomic operation remains exact; takeover then engages | `ACTIVE`/terminal operation at old released generation plus later takeover |
| concurrent | SQLite selects one writer | one of the two rows above, never mixed stale admission | 12 cross-process races matched the selected ordering |
| stale generation | admission uses N after canonical generation changed | reject | no new operation |
| duplicate takeover | exact state already takeover | idempotent | no generation/timestamp rewrite |
| conflicting request | same request ID, changed actor/payload | reject | original request/result retained |
| crash before commit | latch/event/request updated only in uncommitted transaction | rollback | previous exact latch after restart |
