## Authorization taxonomy

1. **Human answer** is one invocation-local Pi/TUI YES or NO. It is not a reusable capability.
2. **Durable authorization** binds one exact protected readiness/handoff/prompt, actor, lifecycle identity, and latch generation.
3. **Admission** is a separate unique row proving that the authorization was consumed for one local operation.
4. **Dispatch intent/attempt** is a separate durable row created before the external call.
5. **Outcome** is separate evidence reported after the call.
6. **Recovery** remains separate. A missing outcome after an intent is not silently converted to failure or retried.

NO creates no authorization, admission, intent, external call, or latch release. Its protected request-ledger result exists only to make the exact invocation request conflict-safe. A fresh later interaction may answer YES. YES followed by a different NO cannot revoke committed authority. Same request ID with a changed answer conflicts.

## Atomic authorization/admission/intent

The final protected YES transaction revalidates:

- exact readiness and reservation digest;
- exact protected ACTIVE lifecycle binding including incarnation;
- exact protected engaged latch generation/reason with no `HUMAN_TAKEOVER`;
- no prior authorization, admission, or dispatch attempt;
- exact authorization/admission/idempotency/dispatch identities.

It then atomically releases the latch, inserts authorization and admission, inserts the single `DISPATCHING` intent, appends authority events, and records the request result. There is no committed authorization-only or admission-without-intent state. Thus the conceptual crash seams “authorization committed before admission” and “admission committed before intent” are structurally unreachable.

A second exact request receives the canonical rows but no external dispatch permit. Different request IDs with the same exact authority identity are idempotent; changed actor/identity conflicts. Independent SQLite clients serialize on `BEGIN IMMEDIATE`, so one caller receives the sole permit.

## State machines

Authorization:

```text
ABSENT -> AUTHORIZED
```

`AUTHORIZED` is immutable. NO leaves it absent. There is no revoke/toggle/reuse transition.

Admission:

```text
ABSENT -> COMMITTED
```

Admission is created atomically with authorization and dispatch intent. It is immutable and unique for handoff, prompt, authorization, and idempotency key.

Dispatch:

```text
ABSENT -> DISPATCHING -> ACKNOWLEDGED
                     \-> DISPATCHED
                     \-> FAILED
                     \-> UNKNOWN
```

Only the exact terminal replay is idempotent; contradictory outcomes conflict. `FAILED` is used only when the external call is known not to have started, such as final target/takeover failure detected after intent but before invocation. Every exception from the external API after invocation begins is conservatively `UNKNOWN`.

## Exact dispatch guarantee

The precise claim is:

- **exactly-once admission:** yes, for one protected readiness identity;
- **exactly-once durable intent:** yes, one attempt-1 row;
- **at-most-once external invocation by the protected workflow:** one new transaction result carries the only dispatch permit; duplicates and restarts receive none;
- **external idempotency:** none exposed by Pi 0.83.0 `sendUserMessage()` for this call;
- **exactly-once provider/session execution:** **not claimed**;
- **ambiguous external result:** remains `DISPATCHING` after crash-before-outcome or becomes protected `UNKNOWN`; automatic retry is forbidden.

A durable intent is committed before the irreversible call. If the call succeeds and P2 crashes before outcome commit, restart sees `DISPATCHING`, does not call again, and requires future reconciliation. This is the intentional boundary to the unmigrated recovery domain.

## Takeover and lifecycle ordering

- takeover or lifecycle supersession before the atomic YES transaction: authorization/admission/intent refused;
- YES transaction first: authorization/admission/intent remain exact;
- a final synchronous protected target/latch reread runs before external invocation; takeover/shutdown observed there records `FAILED` (known not dispatched) and performs zero external calls;
- after external invocation has begun, a transport exception is `UNKNOWN`, not retryable failure;
- simultaneous protected writers produce one SQLite serial ordering;
- same textual session ID with a new lifecycle incarnation cannot satisfy old readiness.

## Crash interpretation

| Seam | Canonical interpretation | Automatic retry |
|---|---|---|
| authorization before admission | unreachable: one transaction | no |
| admission/intent commit before external call | `DISPATCHING`; zero-call crash is conservatively ambiguous on restart | no |
| during external call | `DISPATCHING` until explicit evidence; exception path records `UNKNOWN` | no |
| external success before outcome commit | `DISPATCHING`; external effect may exist | no |
| outcome commit before project projection | canonical terminal outcome wins; projection can be repaired from canonical state without external replay | no |
