### Service SID type result

`RESTRICTED` was physically attempted first. The native service entered, but dynamically linked child processes (both the protected Node copy and `whoami.exe`) failed loader initialization with `0xc0000142`. Broadly granting this service SID across Windows system paths would have been unsafe and was not attempted.

The passing oracle therefore used service SID type `UNRESTRICTED`. This still adds the service-specific SID to the LocalService token. Protected DACLs grant that SID and do **not** grant `S-1-5-19`, so another ordinary LocalService service does not receive canonical access. Actual P1S reads/writes and P0 denials, rather than textual ACLs alone, were tested.

## Broker-down attack result

From real medium P0, actual calls produced `EPERM` or Win32 exit 5 for:

- key open/read/copy/use/delete/replace/rename-over/DACL change;
- canonical read/write/delete/replace/rename-over/directory deletion/DACL change;
- broker read/overwrite/same-path modification/rename/replacement/bin-directory write/DACL change;
- protected parent/root enumeration, deletion, sibling creation, and DACL change;
- service binary path/account/SID type/DACL/delete/start mutation.

P0 could query service state. P0 also created junctions in its own public directory, but access through them and rename-over substitution of protected canonical/bin directories failed with `EPERM`.

P0 could replace/delete/fabricate the public projection and create `OP-FORGED-BY-P0.json`, exactly as expected. The restarted broker loaded canonical sequence 1, not attacker sequence 999, accepted only `OP-POC-AFTER-RESTART`, and ended at sequence 2 with zero forged canonical records. There is no public semantic pipe/RPC; P0's SCM start attempt failed with exit 5 and caused no mutation.

## Restart and crash result

Clean restart used P1S PID 37932 before and PID 28668 after; P2 PIDs were 35104 and 7612. The fingerprint remained stable. The restarted service loaded sequence 1 and accepted the post-restart mutation at sequence 2.

The crash oracle terminated P1S PID 35216 immediately after a complete, flushed `state.json.next` write and before atomic replacement. SCM reported unexpected termination 1067. Canonical SHA-256 remained exactly:

```text

Recovery PID 2252 loaded sequence 2, detected and discarded the stale temporary file, regenerated projection, and retained only the two committed requests. An exact older signed sequence-1 projection replay was ignored. No P2 remained after abrupt P1S exit.

## Important provisioning finding

The initial installer-created directories inherited the invoking user's ownership even after DACL hardening. Because ownership can confer DACL-rewrite authority, this is not acceptable. Before final acceptance, protected parent/root/files were changed to owner `BUILTIN\Administrators`; medium P0 then received Win32 exit 5 changing parent, root, key, canonical, and binary ACLs. The checked-in provisioning PoC now sets protected ownership explicitly before any P0 test.
