## Recovered plan contract

`TASK_PLAN.md` remains the sole **current live** plan authority. `PlanRevisionWriter` retains the accepted exact-byte/revision/content-digest CAS, bounded lock, owner-gate transition, history, final raw attestation and one-rename semantics. Revision-only, digest-only and byte movement are distinct stale conditions. `current_item`, `next_item`, `next_step`, task status and owner gate retain their existing Ledger validation.

A privileged handoff additionally requires one immutable **workflow snapshot**. Historical M-02 selected one detached/deep-frozen P* after the owner-gate transition and before final reservation; checkpoint, manifest and prompt derive only from P*. The selected secure model is therefore both:

1. live TaskLedger authority for the short cooperative owner/CAS capture boundary; and
2. protected immutable P* for the already-reserved privileged workflow.

Later project plan movement remains allowed. It may make live continuity fail under the existing contract, but it cannot rewrite the reserved execution subject or contaminate its artifacts.

The protected snapshot contains only recovery-significant canonical plan semantics:

`task_id`, objective, current/next/next-step, plan revision, exact plan-byte digest, requirements version, completion criteria, decisions, tests, evidence references, minimal reads, canonical required paths, model policy and reasoning policy.

It does not duplicate arbitrary TaskLedger fields, the complete task DAG, timestamps, owner-gate audit fields or display prose.

## Canonicalization and digests

- Current plan content identity: SHA-256 of exact `TASK_PLAN.md` bytes, written as `sha256:<64 lowercase hex>`.
- Protected plan semantic identity: existing strict-JSON clone and canonical JSON over the normalized field set above; required paths are normalized by `canonicalRequiredLocalPaths()`; SHA-256 is the `snapshot_id` / semantic digest.
- Artifact payload content identity: SHA-256 of canonical payload JSON with `content_digest:null`.
- Artifact byte identity: SHA-256 of the exact canonical envelope bytes, including the final newline.
- Relationship identity: SHA-256 of the fixed semantic artifact-registration request.

A task/revision already protected with different canonical snapshot content conflicts. Exact repeats are idempotent. No last-writer-wins or timestamp ordering exists.

## Protected architecture and relationship graph

The existing protected SQLite advances to `aiopago.operation-authority/1.5.0`; the inherited P1S/P2 protocol advances to `/6`.

New minimal tables:

- `plan_authority_snapshots` — immutable canonical semantic snapshot, revision/content/semantic identities and position;
- `handoff_plan_authority` — exact handoff/reservation→snapshot relation;
- `artifact_authority` — checkpoint/manifest byte digest, content digest, handoff, plan snapshot and manifest→checkpoint relation.

Plan snapshot insertion, handoff relation, reservation, active source, reservation event and request result share the existing `BEGIN IMMEDIATE`. A crash cannot expose a reservation without its protected plan subject. A bounded 1.4→1.5 upgrade derives plan snapshots only from already-protected reservation JSON. It deliberately does **not** promote old project artifact indexes/hashes into protected authority; an older unresolved subject without a protected artifact record remains fail-closed and needs explicit later reconciliation. Artifact registration is a separate fixed semantic transaction at each legitimate ArtifactStore creation boundary. A checkpoint must match its reserved ID and protected plan. A manifest additionally requires its reserved ID, the exact ACTIVE protected lifecycle binding and the exact previously registered checkpoint.

The resulting graph is:

```text
task/revision/content
        |
        v
protected plan snapshot <-> protected handoff reservation
        |                         |
        |                         +-> protected lifecycle binding
        v                         |
protected checkpoint <------------+
        |
        v
protected manifest relation
        |
        +-> protected resume readiness -> authorization/admission/dispatch
```

Individually valid objects from different handoffs cannot satisfy the graph.

## Artifact authenticity and TOCTOU

Artifact confidentiality is not claimed or required. P0 may read every byte and may physically rewrite, truncate, rename, delete/recreate, symlink or hardlink files under the project artifact root. Secure verification ignores the project `artifacts` row as expected identity, derives the bounded path from protected kind/ID, reads once, hashes those exact bytes, validates the same in-memory envelope/payload and returns those same detached bytes/payload to the consumer. It does not verify A, close, reopen and consume B.

Path identity is therefore not authority. A symlink or hardlink containing the exact protected bytes has the same content identity; a substituted object with different bytes fails. Project expected hashes and paths may be forged without changing this result.

Registration accepts no arbitrary path and does not ask P1S to hash a caller-selected file. Trusted P2 supplies only the fixed checkpoint/manifest identity produced at the legitimate ArtifactStore boundary. The protocol has no generic blob write, file-signing oracle, arbitrary SQL or `HASH_AND_TRUST_ARBITRARY_PATH` operation.

## Recovery-input readiness sentinel

The narrow read-only check requires:

- exact supplied canonical plan snapshot equal to the protected handoff snapshot;
- actual checkpoint byte/content identity equal to protected expectation;
- actual manifest byte/content identity equal to protected expectation;
- exact manifest→checkpoint→plan→handoff relationship;
- exact ACTIVE lifecycle binding;
- when resume readiness exists, exact readiness→plan/checkpoint/manifest equality.

It returns internal evidence `RECOVERY_INPUT_READY` and `recovery_authority_available:false`. It writes no lifecycle, recovery, reservation, authorization, admission or dispatch state. A protected `DISPATCHING`/`UNKNOWN` row may be reported as the future subject, but is never reconciled here.

## Portable mode

Portable/dev mode retains the existing TaskLedger, project ArtifactStore index and sealed-envelope behavior. It is useful compatibility behavior but is not secure under the R1-M-13 P0 threat model. Secure mode requires the protected recovery-input authority, never substitutes project SQLite after a protected failure and never trusts a project expected digest.

## Remaining boundary

Historical M-07/M-08 continuity recovery remains implemented only in the portable authority path. In secure mode it continues to return `SECURE_RECOVERY_AUTHORITY_UNAVAILABLE`. This slice proves and mutually binds the facts that a later protected recovery/reconciliation domain may consume; it does not decide or execute any recovery transition.
